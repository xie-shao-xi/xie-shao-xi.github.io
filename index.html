minio+kms

MinIO 主备 + SSE-KMS 加密部署实践

内网离线环境下部署两套 MinIO 组成主备（单向桶复制 + 备节点只读），并自建三节点 KMS 集群，为桶启用 SSE-KMS 服务端加密。
文中 IP、主机名、桶名、密钥名、账号均为示例（192.0.2.x / minio-a / app-bucket / app-enclave），请替换为实际环境。

写在前面

适用场景：内网对象存储，服务器无法访问外网，需要使用离线 rpm 安装；两个节点各有一块数据盘，无法组成分布式纠删码集群；业务要求数据在主备之间同步，并对静态数据做服务端加密。

组件版本：MinIO 20250723155402.0.0、mcli 20250721052808.0.0、MinKMS（minkms）同期发布版本；架构 aarch64。

核心结论：

  1. 两个节点、各一块数据盘，只能做”两套独立实例 + 桶复制”的主备，不能组成分布式纠删码集群（分布式模式至少需要 4 块驱动器且分散在多个节点）。
  2. 桶复制依赖版本控制；删除同步需要显式开启 delete 与 delete-marker，否则主节点删除的对象会在备节点残留。
  3. 主备由两层保证：数据层用单向复制，权限层用只读策略限制备节点写入，二者缺一不可。
  4. SSE-KMS 依赖三样东西：可用的 KMS 集群、enclave 与 external key、MinIO 侧的 KMS 连接配置；KMS 不可达时加密写入会失败。
  5. HSM 密钥是整个加密链路唯一的根，丢失后历史对象无法解密，必须离线备份。

以下按”架构规划 → 安装 MinIO → 桶与权限 → 桶复制 → KMS 集群 → 启用 SSE-KMS → Nginx 代理 → 常见问题 → 检查清单”展开。

一、架构与规划

1.1 组件关系

应用 / SDK ──▶ Nginx(:9000) ──▶ minio-a(:9000, 主)
                        └────▶ minio-b(:9000, 备, 只读)

minio-a ──桶单向复制──▶ minio-b
minio-a / minio-b ──mTLS:7373──▶ KMS 集群（kms-node1/2/3）

1.2 节点与端口

节点 角色 地址 端口
minio-a 主节点（可读写） 192.0.2.10 9000 / 9001
minio-b 备节点（只读） 192.0.2.11 9000 / 9001
kms-node1 KMS 节点（兼 MinIO 主机） 192.0.2.10 7373
kms-node2 KMS 节点（兼 MinIO 主机） 192.0.2.11 7373
kms-node3 KMS 节点（应用服务器） 192.0.2.12 7373
nginx 反向代理（主备切换入口） 192.0.2.12 9000
  • 9000：S3 API，业务与 SDK 使用；
  • 9001：管理控制台，按需开放；
  • 7373：MinIO 与 KMS 之间的通信端口，只允许三个 KMS 节点与两台 MinIO 互访。

1.3 操作系统与数据目录

项 值
数据目录 /dmdata/minio/data
日志目录 /dmdata/minio/log
运行用户 minio-user（系统账号，无登录 shell）
配置文件 /etc/default/minio

两台 MinIO 的版本必须一致，否则桶复制与 KMS 接口可能出现不兼容。

1.4 部署顺序

  1. 两台服务器安装 MinIO 并启动；
  2. 建桶、建业务子用户、配置策略（主节点读写、备节点只读）；
  3. 开启版本控制，建立主→备的单向复制规则；
  4. 三台服务器部署 KMS 并组成集群；
  5. 在 KMS 中创建 enclave 与 external key；
  6. 两台 MinIO 配置 KMS 连接并重启；
  7. 为桶设置默认 SSE-KMS，验证加密读写与复制；
  8. 接入 Nginx，完成主备切换验证。

二、安装 MinIO

两台 MinIO 服务器执行相同步骤。

2.1 组件与下载地址

组件 文件 下载地址

sudo tee /etc/default/minio > /dev/null <<'EOF'

三、桶、用户与权限策略

以下操作在主节点执行，之后通过复制规则把数据同步到备节点；备节点只需最后替换为只读策略。

3.1 本地别名

mcli alias set local http://127.0.0.1:9000 【MinIO管理员账号】 【MinIO管理员密码】
mcli admin info local

3.2 创建桶并设为私有

mcli mb local/app-bucket
mcli anonymous set private local/app-bucket
mcli anonymous get local/app-bucket        # 应返回 private

对象存储默认不应公开匿名访问，私有桶通过预签名 URL 提供临时访问。

3.3 创建业务子用户

mcli admin user add local appuser '【业务用户密码】'
mcli admin user list local

业务代码使用子用户的 AccessKey/SecretKey，不使用管理员凭据。

3.4 策略文件

主节点（可写）策略：

cat > app-policy.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": ["arn:aws:s3:::app-bucket/*"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::app-bucket"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetBucketLocation"],
      "Resource": ["arn:aws:s3:::app-bucket"]
    }
  ]
}
EOF

备节点（只读）策略：

cat > app-policy-readonly.json <<'EOF'
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetBucketLocation", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::app-bucket"]
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:GetObjectVersion"],
      "Resource": ["arn:aws:s3:::app-bucket/*"]
    }
  ]
}
EOF

策略只覆盖目标桶，避免子用户越权访问其他桶。

3.5 注册并绑定

mcli admin policy create local app-policy ./app-policy.json
mcli admin policy attach local app-policy --user appuser
mcli admin user info local appuser

备节点上则注册只读策略并绑定同名用户，保证应用切换到备节点时仍有读权限。

3.6 权限验证

# 用业务子用户配置别名
mcli alias set app-test http://127.0.0.1:9000 appuser '【业务用户密码】'

# 预期成功
echo "test" > ~/test.txt
mcli cp ~/test.txt app-test/app-bucket/test.txt
mcli ls app-test/app-bucket/

# 预期失败：访问其他桶
mcli ls app-test/other-bucket/

# 清理
mcli rm app-test/app-bucket/test.txt
mcli alias remove app-test
rm -f ~/test.txt

3.7 业务方接入

业务服务器只需安装 mcli（或直接使用 S3 SDK），并能访问 9000 端口：

mcli alias set minio-b http://192.0.2.11:9000 appuser '【业务用户密码】'

# 私有桶只能用预签名 URL 临时访问
mcli share download --expire 1h minio-b/app-bucket/example.jpg

四、桶复制（主备）

4.1 前提

  • 两台 MinIO 版本一致；
  • 两台服务器 9000 端口互通；
  • 两个桶已存在且均为私有；
  • 待复制桶已开启版本控制。

4.2 双向别名

# 在主节点执行
mcli alias set minio-a http://192.0.2.10:9000 【MinIO管理员账号】 【MinIO管理员密码】
mcli alias set minio-b http://192.0.2.11:9000 【MinIO管理员账号】 【MinIO管理员密码】

mcli admin info minio-a
mcli admin info minio-b

4.3 清理备节点残留

若备节点此前有测试数据，先清空目标桶，避免与复制历史冲突：

mcli rm --recursive --force minio-b/app-bucket

4.4 开启版本控制

mcli version enable minio-a/app-bucket
mcli version enable minio-b/app-bucket

未开启版本控制时，replicate add 会直接失败。

4.5 建立主 → 备的复制规则

mcli replicate add minio-a/app-bucket \
  --remote-bucket minio-b/app-bucket \
  --replicate "delete,delete-marker,existing-objects"

参数含义：

参数 作用
delete 同步对象删除操作
delete-marker 同步删除标记，保证版本语义一致
existing-objects 规则建立前已存在的对象也纳入复制

建立规则时会要求输入远端凭据，使用已配置的别名可以避免在命令行中写明文密码，同时避免 shell 转义问题。

4.6 查看与验证

mcli replicate ls minio-a/app-bucket
mcli replicate status minio-a/app-bucket

echo "replication test $(date)" > ~/repl-test.txt
mcli cp ~/repl-test.txt minio-a/app-bucket/
sleep 5
mcli ls minio-b/app-bucket/
mcli replicate status minio-a/app-bucket

在备节点能看到同名对象即复制生效。replicate status 中若出现 Pending 或 Failed，先检查版本控制与两节点连通性。

4.7 主备模式与双向复制的取舍

本次最终确定为主备，因此：

  • 不建立备 → 主的反向规则；
  • 备节点使用只读策略（3.4）；
  • 应用或 Nginx 只在主节点故障时才把读请求导向备节点。

若确实需要双向复制（两端都可写），则在两台服务器上分别建立规则：

# 备节点 → 主节点（双向复制时才需要）
mcli replicate add minio-b/app-bucket \
  --remote-bucket minio-a/app-bucket \
  --replicate "delete,delete-marker,existing-objects"

双向复制在两端同时写入同一对象时会产生冲突，且两端都必须可写，不建议作为默认方案。

4.8 规则变更

# 查看规则 ID
mcli replicate ls minio-a/app-bucket

# 停用规则（保留配置）
mcli replicate update --id "<规则ID>" --state "disable" minio-a/app-bucket

# 删除规则
mcli replicate rm --id "<规则ID>" minio-a/app-bucket

五、KMS 集群

MinIO 的 SSE-KMS 需要一个 KMS 提供密钥管理能力。本方案不使用第三方 KMS，而是在三台服务器上部署 MinKMS 并组成集群。

注意：不同 MinIO 版本对 KMS 的环境变量命名可能不同，以安装包附带文档与实际启动参数为准。本文以本次部署验证通过的配置为样例。

5.1 准备用户与目录

三台服务器都执行：

sudo groupadd -r minkms-user
sudo useradd -M -r -g minkms-user -s /sbin/nologin minkms-user

sudo mkdir -p /etc/minkms/certs/CAs /mnt/minio-kms
sudo touch /etc/default/minkms

sudo chown -R minkms-user:minkms-user /etc/minkms /mnt/minio-kms /etc/default/minkms
sudo find /etc/minkms -type d -exec chmod 700 {} +
sudo chmod 700 /mnt/minio-kms
sudo chmod 600 /etc/default/minkms

/mnt/minio-kms 建议单独挂载数据盘，用于存放 KMS 自身的数据。

5.2 安装 minkms 二进制

下载地址（见 2.1 的下载源说明）：

https://dl.min.io/aistor/minkms/release/linux-arm64/

目录中同时提供带版本号的二进制、.sha256sum 校验文件与 .asc / .minisig 签名文件。下载并校验：

curl -O https://dl.min.io/aistor/minkms/release/linux-arm64/minkms.RELEASE.2026-11-17T00-11-12Z
curl -O https://dl.min.io/aistor/minkms/release/linux-arm64/minkms.RELEASE.2026-11-17T00-11-12Z.sha256sum

sha256sum -c minkms.RELEASE.2026-11-17T00-11-12Z.sha256sum
# 输出：minkms.RELEASE....: OK

# 校验值文件指向带版本号的文件名，校验通过后再重命名为 minkms
sudo install -m 750 -o minkms-user -g minkms-user \
  minkms.RELEASE.2026-11-17T00-11-12Z /usr/local/bin/minkms

三台服务器都执行，然后验证：

minkms --version

未使用 install 时可等效为：

chmod +x ~/minkms
sudo mv ~/minkms /usr/local/bin/minkms
sudo chown minkms-user:minkms-user /usr/local/bin/minkms
sudo chmod 750 /usr/local/bin/minkms

版本号以实际下载时目录中的最新 RELEASE 为准，三台节点必须使用同一版本。

5.3 生成 TLS 证书

KMS 节点之间以及 MinIO 与 KMS 之间使用 HTTPS，需要一套自签 CA 与各节点证书。

第一步：生成 CA（只需在任意一台执行）

mkdir -p ~/minkms-ca && cd ~/minkms-ca

openssl genrsa -out ca.key 2048

openssl req -x509 -new -nodes -key ca.key -sha256 -days 3650 \
  -out ca.crt \
  -subj "/CN=MinKMS-Cluster-CA"

第二步：为每个节点签发证书

以 node1 为例：

mkdir -p node1 && cd node1

openssl genrsa -out private.key 2048

# CN 使用该节点的主机名
openssl req -new -key private.key -out node1.csr -subj "/CN=kms-node1"

# SAN 必须覆盖全部节点的主机名与 IP，否则 MinIO 或其它节点校验失败
cat > san.cnf <<'EOF'
subjectAltName = @alt_names
[alt_names]
DNS.1 = kms-node1
DNS.2 = kms-node2
DNS.3 = kms-node3
IP.1  = 192.0.2.10
IP.2  = 192.0.2.11
IP.3  = 192.0.2.12
EOF

openssl x509 -req -in node1.csr -CA ../ca.crt -CAkey ../ca.key \
  -CAcreateserial -out public.crt -days 3650 -sha256 \
  -extfile san.cnf

node2、node3 重复上述步骤，只需把 CN 换成对应主机名。SAN 中要一次性写全三个节点的 DNS 与 IP，这样同一份 public.crt 可以在任意节点使用，也便于后续扩容。

第三步：分发并设置权限

每台节点的目录结构：

/etc/minkms/certs/
├── private.key      # 本节点私钥
├── public.crt       # 本节点证书
└── CAs/
    └── ca.crt       # CA 证书，三台相同
sudo chown minkms-user:minkms-user \
  /etc/minkms/certs/private.key \
  /etc/minkms/certs/public.crt \
  /etc/minkms/certs/CAs/ca.crt

sudo chmod 600 /etc/minkms/certs/private.key
sudo chmod 644 /etc/minkms/certs/public.crt
sudo chmod 644 /etc/minkms/certs/CAs/ca.crt

ca.key 只保留在签发机上并离线保管，不分发到各节点。

5.4 统一 /etc/hosts

KMS 集群以主机名互相识别，--host 参数必须与 /etc/hosts 中的名称一致，不能用 IP 代替：

# 三台服务器都要有相同内容
192.0.2.10  kms-node1
192.0.2.11  kms-node2
192.0.2.12  kms-node3

5.5 生成 HSM 密钥

只需在其中一台执行一次，三台节点使用同一个值：

minkms --soft-hsm

输出形如 hsm:aes256:...。该值用于派生 KMS 的主密钥：

  • 立即记录到离线密码库或纸质介质；
  • 三台节点的 /etc/default/minkms 必须完全一致；
  • 丢失该值后，已加密的历史对象无法解密，且无法通过任何配置文件恢复。

5.6 节点配置

/etc/default/minkms：

MINIO_KMS_HSM_KEY=hsm:aes256:【上一步生成的密钥值】
MINIO_KMS_VOLUME=/mnt/minio-kms
MINIO_KMS_OPTS="--host kms-node1:7373 --config /etc/minkms/config.yaml"

--host 逐台替换为本节点的主机名。

/etc/minkms/config.yaml：

sudo tee /etc/minkms/config.yaml > /dev/null <<'EOF'
version: v1
tls:
  certs:
    - key: /etc/minkms/certs/private.key
      cert: /etc/minkms/certs/public.crt
  ca: /etc/minkms/certs/CAs
EOF

6.1 创建 enclave 与密钥

sudo MINIO_KMS_SERVER=https://kms-node1:7373 \
     MINIO_KMS_API_KEY="【API Key】" \
     minkms ls-key -e app-enclave

6.2 MinIO 侧配置 KMS 连接

两台 MinIO 的 /etc/default/minio 追加：

# 三个 KMS 节点都要列出，主机名与 /etc/hosts 一致
MINIO_KMS_SERVER="https://kms-node1:7373,https://kms-node2:7373,https://kms-node3:7373"
MINIO_KMS_ENCLAVE="app-enclave"
MINIO_KMS_SSE_KEY="app-encryption-key"
MINIO_KMS_API_KEY="【API Key】"

要列出全部节点而不是单个地址：单节点不可达时 MinIO 仍可连接其他 KMS 节点，避免加密写入直接失败。

6.3 让 MinIO 信任 KMS 的 CA

sudo cp /etc/minkms/certs/CAs/ca.crt /etc/pki/ca-trust/source/anchors/minkms-ca.crt
sudo update-ca-trust

sudo systemctl restart minio
sudo journalctl -u minio -n 50 --no-pager

日志中应显示 KMS 连接成功。若出现 certificate signed by unknown authority，说明 CA 未加入信任库；出现连接超时则检查 7373 端口与 /etc/hosts。

七、Nginx 反向代理

7.1 为什么需要代理

应用只配置一个入口地址，主节点故障时由 Nginx 切到备节点；同时可以统一做 TLS、限流与访问日志。

7.2 upstream 配置

主备模式（推荐）：

upstream minio_backend {
    server 192.0.2.10:9000 max_fails=3 fail_timeout=15s;   # 主节点
    server 192.0.2.11:9000 backup;                         # 备节点，仅主节点不可用时启用
    keepalive 32;
}

负载均衡模式（两端都可写、且已配置双向复制时才适用）：

upstream minio_backend {
    server 192.0.2.10:9000 max_fails=3 fail_timeout=30s;
    server 192.0.2.11:9000 max_fails=3 fail_timeout=30s;
    least_conn;
    keepalive 32;
}

7.3 server 配置

server {
    listen 9000;
    server_name _;

    location / {
        proxy_pass http://minio_backend;
        proxy_http_version 1.1;

        # 关键：原样透传 Host，S3 签名与 Host 绑定
        proxy_set_header Host $http_host;

        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";

        # 大文件上传不落盘、不限大小
        proxy_buffering off;
        client_max_body_size 0;
        proxy_read_timeout 300s;
        proxy_cache_convert_head off;

        proxy_next_upstream error timeout http_502 http_503 http_504;
        proxy_next_upstream_tries 2;
    }
}

配置检查与生效（容器化 Nginx 的写法）：

sudo docker exec nginx-web nginx -t
sudo docker exec nginx-web nginx -s reload
sudo docker logs --tail 100 nginx-web

7.4 预签名 URL 的 Host 问题

S3 预签名 URL 的签名包含 Host。如果代理改写了 Host（例如把 Host 固定成后端地址），签名校验会失败并返回 403 SignatureDoesNotMatch。

两条规则：

  • 客户端用哪个地址签名，代理就必须把同一个 Host 透传给 MinIO；
  • Nginx 不应使用 proxy_set_header Host 将 Host 改写为后端 IP 或别名。

验证：

# 通过代理生成预签名 URL
mcli alias set minio-proxy http://192.0.2.12:9000 appuser '【业务用户密码】'
mcli share download --expire 1h minio-proxy/app-bucket/example.jpg

# 用返回的 URL 直接访问，应返回 200 与文件内容
curl -I 'http://192.0.2.12:9000/app-bucket/example.jpg?X-Amz-Algorithm=...'

7.5 主备切换验证

# 停止主节点
sudo systemctl stop minio      # 在 minio-a 上执行

# 通过代理读取，应自动落到备节点
curl -I http://192.0.2.12:9000/minio/health/live

# 恢复主节点
sudo systemctl start minio

切换到备节点时，写入会因只读策略返回 403 AccessDenied，这属于预期行为：主备模式下备节点只承接读流量。

八、常见问题

8.1 两个节点能否组成分布式集群

不能。分布式纠删码模式要求驱动器数量与节点分布满足最低要求（至少 4 块驱动器，且不允许单节点承载全部驱动器）。两个节点各一块数据盘，只能部署两套独立实例，用桶复制保持数据同步。

8.2 复制规则创建失败

  • 目标桶未开启版本控制；
  • 远端别名密码含特殊字符导致解析错误，改用交互式输入而非命令行明文；
  • 两端 MinIO 版本差异过大，replicate 子命令不兼容；
  • 9000 端口不通或 DNS 解析失败。

8.3 对象复制了但删除不同步

创建规则时需要显式声明 --replicate "delete,delete-marker,existing-objects"。规则建立后也可以更新：

mcli replicate update --id "<规则ID>" --replicate "delete,delete-marker" minio-a/app-bucket

8.4 备节点仍可写入

备节点上的业务用户绑定了可写策略。把备节点策略替换为 3.4 的只读版本，并确认 mcli admin user info 显示的是只读策略。

8.5 minkms 启动失败

按顺序排查：

  1. /etc/default/minkms 中 --host 是否为本节点的 hostname，且与 /etc/hosts 一致；
  2. private.key 与 public.crt 的权限是否为 600/644，属主是否为 minkms-user；
  3. /mnt/minio-kms 是否存在且属主正确；
  4. journalctl -u minkms -n 100 中的具体报错。

8.6 minkms 命令报 x509 证书错误

CA 未加入系统信任库。执行 5.9 的 update-ca-trust 后重试，或在过渡阶段加 -k。

8.7 MinIO 启动报 KMS 不可用

  • 7373 端口未放行；
  • MINIO_KMS_SERVER 中的主机名无法解析；
  • MinIO 未信任 KMS 的 CA；
  • KMS 集群中至少一个节点不可达。

先确认 minkms ls 能正常返回，再重启 MinIO。

8.8 预签名 URL 返回 403 SignatureDoesNotMatch

签名中的 Host 与请求实际到达 MinIO 时的 Host 不一致。检查 Nginx 是否改写了 Host，以及客户端签名时使用的域名/端口是否与访问地址一致。

8.9 控制台能登录但应用上传失败

  • 应用使用的是管理员账号而非子用户，或子用户策略缺少 s3:PutObject；
  • 桶为私有但应用直接拼接 URL 访问，应改用预签名 URL；
  • 检查 Nginx 的 client_max_body_size 与超时设置。

十、小结

本次部署的要点集中在四处：

  1. 架构选择：两个节点只能做”独立实例 + 桶复制”的主备，分布式纠删码需要更多驱动器与节点；
  2. 主备的双层保证：数据层靠单向复制与版本控制，权限层靠备节点的只读策略，只做其中一层都会出现”备节点被写入”或”删除不同步”；
  3. KMS 的启动顺序依赖：证书与 hosts 先就位，KMS 集群先健康，再配置 MinIO 的 KMS 连接，最后才启用桶加密，否则 MinIO 启动或写入会直接失败；
  4. 根密钥只有一份：HSM 密钥丢失等于历史密文永久不可读，备份优先级高于任何配置文件。

Redis 主从 + Sentinel 哨兵部署实践

内网离线环境下，用源码编译部署一主一从 Redis，并在三台服务器上运行 Sentinel 实现自动故障转移。
文中 IP、主机名、密码、账号均为示例（192.0.2.x / node-a / 【Redis密码】），请替换为实际环境。

写在前面

适用场景：内网自建 Redis，服务器无法访问外网，操作系统为国产化发行版（Kylin V10 / aarch64 同类环境），需要主从复制加自动故障转移，但不使用 Redis Cluster 分片。

版本：Redis 8.10.0（源码编译，仅核心版）；Sentinel 与 Redis 同一套二进制。

节点规划：两台数据库服务器承担一主一从，一台应用服务器只运行 Sentinel，共三个哨兵满足 quorum=2 的要求。

核心结论：

  1. Sentinel 只负责监控与故障转移，不存储数据、不分片；数据仍由主从复制同步，容量上限等于单机内存。
  2. 哨兵数量建议为 3 个，quorum 设为 2：既能在单点故障时完成选举，又能避免出现两个哨兵互相认定对方失联的脑裂。
  3. 离线 + 国产化系统只编译核心版（MALLOC=libc，不加载 modules），完整编译常因模块依赖失败。
  4. 应用必须通过 Sentinel 获取主节点地址，不能写死主节点 IP，否则故障转移后仍连旧主。

以下按”架构规划 → 安装 Redis → 配置主从 → 自启与日志 → 部署 Sentinel → 故障转移验证 → 运维 → 常见问题 → 检查清单”展开。

replicaof 只是初始拓扑。哨兵完成一次故障转移后会重写该配置，届时手工修改可能被覆盖，正确做法是通过哨兵变更拓扑。

3.4 关于脑裂防护

min-replicas-to-write 要求”至少 N 个从节点在线才允许写入”。本架构只有一主一从，主节点一旦与从节点失联，在线从节点数为 0，该配置会导致主节点拒绝所有写入，反而扩大故障范围，因此保持默认关闭：

# min-replicas-to-write 0
# min-replicas-max-lag 10

若后续扩展为”一主多从”，再考虑开启。

四、systemd 自启与日志轮转

4.1 停止脚本

Redis 由 systemd 托管且配置了 Restart=always，直接 kill 会被自动拉起。停止脚本从配置文件读取密码，避免把密码明文写进 unit 文件：

sudo tee /usr/local/redis/bin/redis-stop.sh > /dev/null <<'SCRIPT'
#!/bin/bash
CONF=/usr/local/redis/redis-8.10.0/redis.conf
PASS=$(awk '/^[[:space:]]*requirepass[[:space:]]/ {print $2; exit}' "$CONF" \
  | sed -e 's/^"//' -e 's/"$//' -e "s/^'//" -e "s/'$//")
if [ -z "$PASS" ]; then
  echo "redis-stop: requirepass not found or empty in $CONF" >&2
  exit 1
fi
REDISCLI_AUTH="$PASS" /usr/local/redis/bin/redis-cli shutdown
SCRIPT

sudo chmod 700 /usr/local/redis/bin/redis-stop.sh
sudo chown root:root /usr/local/redis/bin/redis-stop.sh

4.2 服务单元

# /etc/systemd/system/redis.service
[Unit]
Description=Redis Server
After=network.target

[Service]
Type=forking
ExecStart=/usr/local/redis/bin/redis-server /usr/local/redis/redis-8.10.0/redis.conf
ExecStop=/usr/local/redis/bin/redis-stop.sh
Restart=always

[Install]
WantedBy=multi-user.target

启用：

sudo systemctl daemon-reload
sudo systemctl enable redis
sudo systemctl start redis
sudo systemctl status redis

该单元未指定 User=，服务以 root 运行。如需改为专用账号，需同时调整 /data/redis 属主、pidfile 与日志文件属主，并确认该账号对 /data/redis 有读写权限。

4.3 日志轮转

sudo tee /etc/logrotate.d/redis > /dev/null <<'EOF'
/data/redis/logs/redis-server.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
EOF

使用 copytruncate 的原因是无需向 Redis 发送重开日志的信号，也就不需要在轮转脚本中处理密码；代价是轮转瞬间可能丢失少量日志。

强制轮转并触发一条日志确认新文件生效：

REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli CONFIG SET loglevel verbose
REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli CONFIG SET loglevel notice
ls -l /data/redis/logs/

五、部署 Sentinel

5.1 为什么第三台也要装 Redis

Sentinel 由 redis-sentinel 启动，该文件来自 Redis 安装包。第三台应用服务器不需要运行 Redis 实例，但需要这份二进制，因此同样执行第二节的编译安装，只是不启动 redis-server。

5.2 配置目录与文件

三台服务器都执行：

sudo mkdir -p /usr/local/redis/sentinel /data/redis/sentinel
sudo chown -R $(whoami):$(whoami) /usr/local/redis/sentinel /data/redis/sentinel
sudo chmod 700 /usr/local/redis/sentinel

sudo touch /usr/local/redis/sentinel/sentinel.conf
sudo chmod 600 /usr/local/redis/sentinel/sentinel.conf
sudo chown $(whoami):$(whoami) /usr/local/redis/sentinel/sentinel.conf

5.3 sentinel.conf

# /usr/local/redis/sentinel/sentinel.conf
port 26379
daemonize yes
pidfile /data/redis/sentinel/sentinel.pid
logfile /data/redis/sentinel/sentinel.log
dir /data/redis/sentinel

# mymaster 为集群名称，三台必须完全一致
sentinel monitor mymaster 192.0.2.10 6379 2

# 与 Redis 的 requirepass 保持一致
sentinel auth-pass mymaster 【Redis密码】

# 5 秒无响应判定主观下线
sentinel down-after-milliseconds mymaster 5000
# 故障转移超时时间
sentinel failover-timeout mymaster 60000
# 每次只允许一个从节点与新主同步
sentinel parallel-syncs mymaster 1

参数含义：

参数 作用
monitor ... 2 2 是 quorum：至少 2 个哨兵认可主节点失联，才进入客观下线
auth-pass 哨兵连接 Redis 时使用的密码，必须与 requirepass 一致
down-after-milliseconds 主观下线判定时间，过小会误判、过大会延长故障窗口
failover-timeout 同一次故障转移的最长处理时间，也用于抑制重复切换
parallel-syncs 新主产生后同时向新主同步的从节点数量，设为 1 可降低新主压力

Sentinel 运行中会重写该文件，追加 myid、known-sentinel、known-replica 等内容。需要调整参数时优先使用 SENTINEL SET，避免在哨兵运行时直接编辑配置文件。

5.4 启动与集群验证

三台都启动：

查看任一哨兵的视图：

预期：

查看其他哨兵的信息：

sentinels=1 说明只有自己，通常是 26379 端口未互通，或三台配置里的 mymaster 名称不一致。

六、故障转移验证

6.1 记录当前主节点

/usr/local/redis/bin/redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

输出两行：IP 与端口，记下当前主节点。

6.2 停止主节点

sudo systemctl stop redis

systemctl stop 会阻止 Restart=always 自动拉起，因此这是模拟宕机的正确方式；直接 kill 进程会被 systemd 重启。

6.3 观察切换

# 哨兵日志中应出现 +sdown（主观下线）→ +odown（客观下线）→ +switch-master
sudo tail -f /data/redis/sentinel/sentinel.log

# 查询新的主节点
/usr/local/redis/bin/redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

+switch-master 行会打印旧主与新主地址，从节点的角色同时发生改变。

6.4 验证新主可写、旧主可回

在新主上写入：

启动原主节点：

sudo systemctl start redis

哨兵会把它重新配置为从节点，原主节点上执行 INFO replication 应显示 role:slave 且 master_host 指向新主。若原主仍为 master，检查哨兵日志与 failover-timeout，必要时等待一次完整切换周期。

七、运维要点

7.1 停止与修改配置

由于配置了自动重启，停止服务需用 systemctl stop，并确认进程与端口都已释放：

sudo systemctl stop redis
ps -ef | grep redis-server | grep -v grep
ss -tlnp | grep 6379

# 修改配置后
sudo systemctl start redis

7.2 避免手工修改被托管的配置

  • redis.conf 中的 replicaof 会被哨兵改写；
  • sentinel.conf 运行中会被追加 myid、已知哨兵、已知从节点等信息。

调整哨兵参数使用：

/usr/local/redis/bin/redis-cli -p 26379 SENTINEL SET mymaster down-after-milliseconds 5000

7.3 密码与权限

  • redis.conf 建议 600，sentinel.conf 同样 600；
  • 密码通过 REDISCLI_AUTH 环境变量传递，避免出现在 ps 与 shell history 中；
  • 对外只开放必要的来源网段，不应将密码作为唯一防线。

7.4 容量与持久化

  • 容量上限为单机内存，maxmemory 与淘汰策略需按业务设置；
  • 数据盘要预留 RDB 快照与 AOF 重写的空间，日志同样放在数据盘；
  • 内存不足时先扩容而不是依赖哨兵，哨兵只解决可用性问题。

八、常见问题

8.1 编译失败（jemalloc 或模块相关）

离线环境与国产化系统上，完整编译依赖较多。只编译核心：

cd src
sudo make distclean
sudo make MALLOC=libc -j$(nproc)
sudo make PREFIX=/usr/local/redis install

8.2 从节点报 NOAUTH 或复制不建立

  • 从节点 masterauth 是否与主节点 requirepass 一致；
  • 主节点 bind 与 protected-mode 是否允许从节点连接；
  • 主节点 6379 是否对从节点放行。

8.3 客户端提示连接被拒绝

protected-mode yes 且未设置 bind 允许地址时，Redis 只接受本机连接。确认 bind 与 protected-mode 的组合，并检查 iptables 与安全组。

8.4 哨兵只看到自己（sentinels=1）

  • 26379 是否三台互通；
  • 三台配置中 mymaster 名称是否完全一致；
  • 是否存在重复启动的哨兵进程占用不同配置文件。

8.5 主节点宕机但没有触发切换

  • quorum 是否满足：三个哨兵中至少两个判定客观下线；
  • down-after-milliseconds 是否过大；
  • 哨兵日志中是否出现 +sdown 但缺少 +odown（说明另一台哨兵未认可）。

8.6 日志没有轮转

  • 检查 /etc/logrotate.d/redis、redis-sentinel 是否存在且语法正确；
  • 使用 copytruncate 时不需要 create，若同时存在可能产生空文件；
  • 手动执行一次 logrotate --force 观察输出。

8.7 故障转移后应用仍连旧主

应用写死了主节点地址。改为只配置哨兵地址与 mymaster 名称，由客户端库完成主节点发现。

svnlook info 输出作者、提交时间与提交说明，可据此判断各仓库最近是否仍在使用。若多数仓库的最后提交时间距今较远，可按 1.3 的方式先做不停机的全量预演。

1.2 需要迁移的四类内容

内容 旧服务器位置 迁移方式
仓库数据 repo/<仓库名> svnadmin dump → svnadmin load
仓库配置与钩子 repo/<仓库名>/conf、repo/<仓库名>/hooks tar 打包 → 解压覆盖
全局账号与权限 repo/authz、repo/passwd tar 打包 → 解压 → 修正权限位
Web 管理端数据 project/sqlite.db、log、temp tar 打包 → 解压 → 修正属主

注意 authz/passwd 位于仓库根目录（/data/svn/data/project/repo/），不在单个仓库内；各仓库 conf/svnserve.conf 通过相对路径引用它们，因此解压后需要确认相对路径仍然有效。

1.3 是否需要停机

两种做法：

  • 仓库最近无提交：可以不停机完成全量 dump/load 预演，切换域名前再补一次增量（见 8.7），最后统一停止旧服务。
  • 仓库仍在活跃使用：建议在约定窗口内停止 svnserve 与 svnWebUI 后再 dump，避免 dump 过程中产生新版本导致与 conf 时间点不一致。

无论哪种方式，域名切换完成前旧服务不要重新对外开放写入。

二、方案选型

方案 A：一次性全量 dump 方案 B：按版本区间分段 dump 方案 C：服务器间直接 rsync
适用 单仓库体积小于中转上限 大仓库，单个 dump 超过 20 GB 新旧服务器网络互通，不经堡垒机
传输 中转机上传下载 分段后分别传输、分别 load rsync 直接推送
复杂度 低 中，需保证 load 顺序 低，但要求网络可达
本次采用 小仓库 大仓库 备选

分段的核心是 --deltas --incremental：第一段使用 --deltas，后续段追加 --incremental，load 时严格按顺序执行，否则版本号会错乱。

3.3 打包配置与钩子

cd /data/svn/data/project/repo

# 各仓库的 conf 与 hooks

  tar czf /data/svn-dump/${r}-conf.tar.gz -C "$r" conf hooks

3.4 小仓库直接 dump

cd /data/svn/data/project/repo

  echo ">>> $(date '+%F %T') dumping $r ..."
  svnadmin dump "$r" --deltas | gzip -1 > /data/svn-dump/${r}.dump.gz
  echo ">>> $(date '+%F %T') $r 完成"
  ls -lh /data/svn-dump/${r}.dump.gz
done

--deltas 让 dump 以增量表示存储，体积明显小于默认的全量表示；gzip -1 以较低压缩率换取更高的压缩速度，适合大仓库。

3.5 大仓库后台 dump

单个仓库 dump 可能持续数小时，放入后台执行并记录日志：

nohup bash -c '
  cd /data/svn/data/project/repo
  for r in project-d project-e; do
    echo ">>> $(date) dumping $r"
    svnadmin dump "$r" --deltas | gzip -1 > /data/svn-dump/${r}.dump.gz
    echo ">>> $(date) $r done"
  done
' > /data/svn-dump/dump.log 2>&1 &

tail -f /data/svn-dump/dump.log

3.6 按版本区间分段 dump

当单个仓库的 dump 文件超过中转限制时，按版本区间切分。以下示例将仓库拆为 0、1-5、6-10、11、12 五段：

nohup bash -c '
REPO=/data/svn/data/project/repo/project-d
DUMP_DIR=/data/svn-dump
LOG=$DUMP_DIR/dump_project_d.log

echo ">>> $(date) start 0:0" >> "$LOG"
(svnadmin dump "$REPO" -r 0 --deltas | gzip -1 > "$DUMP_DIR/project-d.0.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 1:5" >> "$LOG"
(svnadmin dump "$REPO" -r 1:5 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.1-5.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 6:10" >> "$LOG"
(svnadmin dump "$REPO" -r 6:10 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.6-10.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 11" >> "$LOG"
(svnadmin dump "$REPO" -r 11 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.11.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 12" >> "$LOG"
(svnadmin dump "$REPO" -r 12 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.12.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) all done" >> "$LOG"
' &

tail -f /data/svn-dump/dump_project_d.log

分段原则：

  • 段与段之间必须首尾相接，不重不漏（0、1-5、6-10…）；
  • 只需第一段不带 --incremental，其余段都带；
  • 某一段体积仍超限时，继续按更小的版本区间细分，不要改用 split 切分 dump 文件：分片无法单独校验，出问题时难以定位。

3.7 校验与传输

在旧服务器生成校验值，下载到本地、上传到新服务器后分别校验，三处结果必须一致。校验文件使用相对路径记录，便于在新服务器同目录下复核：

cd /data/svn-dump
md5sum *.dump.gz > md5.txt

# 新服务器：将 md5.txt 与 dump 文件放在同一目录后执行
cd /home/admin_svn/svn-import
md5sum -c md5.txt

若单个文件仍需经堡垒机中转：

split -b 5000M -d -a 3 project-d.0.dump.gz project-d.0.part_
cat project-d.0.part_* > project-d.0.dump.gz

Windows 侧可用 certutil -hashfile <文件> MD5 计算校验值。

5.2 分段仓库按顺序 load

cd /data/svn/data/project/repo
svnadmin create project-d

nohup bash -c '
  cd /data/svn/data/project/repo
  for f in project-d.0 project-d.1-5 project-d.6-10 project-d.11 project-d.12; do

    gzip -dc /home/admin_svn/svn-import/${f}.dump.gz | svnadmin load /data/svn/data/project/repo/project-d
    echo ">>> $(date) $f done"
  done
  echo ">>> $(date) all load done, starting verify ..."
  svnadmin verify /data/svn/data/project/repo/project-d
  echo ">>> $(date) verify done"
' > /home/admin_svn/svn-import/load-project-d.log 2>&1 &

顺序必须与 dump 时的版本区间顺序一致（0 → 1-5 → 6-10 → 11 → 12）。顺序错误或漏段时，load 会因版本号冲突失败或产生错误的历史。

八、常见问题

8.1 能否直接拷贝仓库目录

可以在同版本、同路径的前提下用 svnadmin hotcopy 或直接复制目录，但要求两端路径完全一致、版本一致，且无法在传输中压缩和分段。使用 dump/load 可以获得可校验的中间产物，并在加载时逐段确认，更适合跨机器、跨中转的迁移。

8.2 单个 dump 文件超过中转限制

三种处理方式，按优先级：

  1. 按版本区间分段 dump（3.6），最易校验；
  2. split 分片传输后合并，合并后必须校验 md5/sha256；
  3. 新旧服务器网络互通时改用 rsync 直接传输，绕过堡垒机。

8.3 分段 load 顺序错误会怎样

load 会因版本号不连续报错，或把后续段加载到错误的版本上。判断方法：加载完成后用 svnlook youngest 与基线比对，并抽查 svn log 的版本号连续性。

8.4 恢复 conf/hooks 后相对路径失效

svnserve.conf 中的 authz-db、password-db 是相对 conf/ 目录的路径。只要新服务器目录结构与旧服务器一致（repo/<仓库>/conf 与 repo/authz、repo/passwd 的相对关系不变），路径即有效。恢复后统一用以下命令确认：

grep -E 'authz-db|password-db' /data/svn/data/project/repo/*/conf/svnserve.conf

8.5 迁移后用户无法登录

依次确认：

  1. 全局 passwd 是否恢复到位，权限是否为 600；
  2. 各仓库 svnserve.conf 的 password-db、authz-db 是否指向正确的全局文件；
  3. svnserve 进程是否有权限读取上述文件（admin_svn 属主）；
  4. 若账号由 svnWebUI 维护，确认 sqlite.db 已恢复且启动顺序正确（5.5）。

8.6 svnWebUI 启动后账号或权限文件被改写

管理端启动时可能依据数据库重建 authz/passwd。规避方式：

  • 先恢复 sqlite.db 再启动管理端；
  • 启动后立即用 wc -c 对比文件大小；
  • 保留一份 authz.bak.$(date +%F)、passwd.bak.$(date +%F) 作为回退。

8.7 迁移期间有人提交

对仍在使用的仓库，在切换窗口内先停止服务，再以迁移前记录的基线版本为起点导出增量并加载（示例中基线为 r100）：

svnadmin dump /data/svn/data/project/repo/project-a \
  -r 101:HEAD --deltas --incremental | gzip -1 > /data/svn-dump/project-a.inc.dump.gz

加载顺序仍为”全量段 → 增量段”。

8.8 如何确认数据完整

  • svn log 抽查最新版本与提交人、提交说明。

适用场景：单机 Omnibus 部署的 GitLab CE，内网自建，服务器无法访问外网（全程离线包），需要更换服务器并同时升级版本。

核心结论：

  1. 版本号必须完全一致，包括小版本号；CPU 架构与操作系统小版本不影响。
  2. 主要数据量在仓库（repositories），数据库与元数据通常只有几百 MB，因此方案的核心是仓库的传输方式。

一、迁移前必须确认的三件事

1.1 版本号：必须完全一致

GitLab 恢复时会强校验版本：备份包文件名中包含版本号（如 ..._17.5.1_gitlab_backup.tar），版本不一致时恢复会被拒绝。

  • gitlab-ce-17.5.1 只能恢复到 gitlab-ce-17.5.1；
  • 替换为 gitlab-jh-17.5.1（极狐版）不可行；
  • 替换为 gitlab-ce-17.5.10 同样不可行。

因此流程必须是：先安装同版本 → 恢复数据 → 再升级，而不是直接安装新版本再导入数据。

架构不同不影响迁移：旧服务器 x86_64、新服务器 aarch64 也可以迁移，因为仓库是文件、数据库是逻辑备份，只需使用对应架构的安装包。

查看旧服务器版本：

# 方式一：命令行
sudo gitlab-rake gitlab:env:info

# 方式二：网页右上角 帮助 → 帮助页，地址为 域名/help

1.2 主要数据量在仓库

典型迁移的体积分布如下（示例）：

内容 位置 量级
仓库数据 git_data_dirs 指定目录 几十 GB，占 95% 以上
数据库 + 元数据 PostgreSQL / Redis / 附件等 几百 MB
配置文件与密钥 /etc/gitlab/ 几 KB，但丢失后无法恢复

这决定了方案设计：仓库通过 rsync 增量同步，其余数据使用 gitlab-backup 打包恢复。

1.3 两个必须备份的文件

  • /etc/gitlab/gitlab.rb：所有配置（域名、目录、证书、邮件、备份路径）。
  • /etc/gitlab/gitlab-secrets.json：数据库加密密钥、CI secrets、2FA 密钥等。缺少该文件时，恢复后的实例无法解密加密字段，用户无法登录，Runner token 全部失效。

同时备份 SSH 主机密钥，避免迁移后客户端 known_hosts 报主机密钥变更：

sudo cp /etc/gitlab/gitlab-secrets.json  ~/backup/
sudo cp -r /etc/gitlab/ssl/              ~/backup/
sudo cp /etc/ssh/ssh_host_*              ~/backup/
tar -czf backup.tar.gz -C ~ backup

二、方案选型：全量停机 vs 预同步

方案 A：全量停机备份 方案 B：rsync 预同步 + 轻量恢复
步骤 停机 → 全量备份（含仓库）→ 传输 → 恢复 提前 rsync 仓库 → 窗口内只做增量 + 轻量备份 → 恢复
停机时长 与总数据量成正比，几十 GB 可能需要数小时 只与增量和数据库大小相关，通常 30~60 分钟
操作复杂度 低，一条命令 中，需处理 rsync 权限、路径、两次备份
适用场景 数据量小（< 20 GB）、窗口充裕 仓库较大、窗口紧张（本文采用）

方案 B 的关键点：**仓库不参与 gitlab-backup**（SKIP=repositories），只备份数据库和元数据；仓库通过 rsync 保持同步。这样备份包从几十 GB 缩减到几百 MB，传输和恢复均为分钟级。

代价是需要额外处理两件事：rsync 传输中的属主保留，以及恢复后 GitLab 如何重新识别仓库。

三、准备阶段

新服务器从零开始，按以下顺序操作。

3.1 打通网络与端口

旧服务器需能连接新服务器的 SSH（迁移时通过 rsync 推送数据），新服务器的 443 端口需对内网开放（用于验证与后续访问）。

第一步：在新服务器增加 10022 端口（保留 22 端口，避免无法远程登录）

sudo vi /etc/ssh/sshd_config
# 新增
Port 22          # 默认端口，可能未显式配置，需补充
Port 10022       # 迁移专用

# 先校验配置语法再重启
sudo sshd -t
sudo systemctl restart sshd

第二步：放行防火墙

iptables 环境（-I 表示插入到指定行，行号以实际环境为准）：

sudo iptables -L -n --line-numbers      # 查看现有规则与行号

sudo iptables -I INPUT 19 -p tcp -s 0.0.0.0/0 --dport 443   -j ACCEPT
sudo iptables -I INPUT 20 -p tcp -s 0.0.0.0/0 --dport 10022 -j ACCEPT

sudo service iptables save              # 保存规则，否则重启后失效
sudo iptables -L -n --line-numbers      # 复查

安全建议：10022 仅对旧服务器 IP 开放，迁移完成后可移除该规则。

firewalld 环境：

sudo firewall-cmd --add-port=443/tcp   --permanent
sudo firewall-cmd --add-port=10022/tcp --permanent
sudo firewall-cmd --reload

第三步：从旧服务器验证

ssh -p 10022 admin_gitlab@192.0.2.10

3.2 数据盘配置为 LVM 并挂载到 /data

仓库目录不要放在系统盘，几十 GB 数据容易占满根分区。

sudo vgcreate vg_data /dev/vdb
sudo lvcreate -l 100%FREE -n lv_data vg_data

sudo mkfs.xfs /dev/vg_data/lv_data

sudo mkdir -p /data
sudo mount /dev/vg_data/lv_data /data

fstab 中使用 UUID（设备名可能变化）：

sudo blkid /dev/vg_data/lv_data
sudo cp /etc/fstab /etc/fstab.bak
sudo vim /etc/fstab
# 末尾追加（UUID 替换为上一条命令输出的值）
# UUID=【你的UUID】 /data xfs defaults 0 0

验证配置并重启确认：

df -h /data
lsblk
sudo reboot

3.5 修改 gitlab.rb

迁移场景下不建议直接沿用旧服务器的全部配置，仅保留必要项：

# 对外域名，必须与最终访问地址一致（影响 clone 地址、OAuth 回调、CI 变量）
external_url "https://git.example.com"

# 备份目录：放到数据盘
gitlab_rails['backup_path'] = "/data/gitlab/backups"

# 仓库目录：放到数据盘
git_data_dirs({
  "default" => {
    "path" => "/data/gitlab/git-data"
  }
})

# SSL 证书
nginx['ssl_certificate']     = "/etc/gitlab/ssl/server.crt"
nginx['ssl_certificate_key'] = "/etc/gitlab/ssl/server.key"

# 临时让 Nginx 额外监听新服务器内网 IP，便于切换域名前用 IP 验证
# 注意：此处只增加 listen，不修改 external_url
nginx['custom_gitlab_server_config'] = "listen 192.0.2.10:443 ssl;"

external_url 与通过 IP 访问存在冲突：GitLab 生成的所有链接均以 external_url 为准。增加 listen 仅用于 DNS 切换前访问，页面内跳转仍指向域名，因此用 IP 验证时需直接访问仓库地址，或在本机配置 hosts。

四、预同步（不停机）

目标是在正式窗口前尽可能同步新服务器的仓库目录，减少停机期间的工作量。该步骤可在业务时间执行，不影响旧服务器。

4.1 记录基线

迁移前后各跑一次，避免漏提交。命令也可以存成脚本文件，更可靠。

sudo tee /tmp/list_last_commit.rb > /dev/null <<'EOF'
# 输出每个项目的最后提交时间，用于迁移前后对比
Project.find_each do |project|
  next unless project.repository_exists?

  begin
    last_commit = project.repository.commit
    next unless last_commit

    puts "#{project.full_path} | #{last_commit.committed_date.utc.strftime('%Y-%m-%d %H:%M:%S')}"
  rescue StandardError => e
    puts "#{project.full_path} | ERROR: #{e.class}"
  end
end
EOF

sudo gitlab-rails runner /tmp/list_last_commit.rb | sort > /tmp/last_commit.before.txt
wc -l /tmp/last_commit.before.txt

同时确认仓库总量，用于估算 rsync 耗时：

sudo du -sh /data/gitlab/git-data/repositories

4.2 先 dry-run 再正式同步

源路径以旧服务器 gitlab.rb 中 git_data_dirs 的实际配置为准：默认安装为 /var/opt/gitlab/git-data/repositories，本文示例统一写作数据盘上的 /data/gitlab/git-data/repositories。

dry-run 只列出差异，不传输数据，可用于确认路径、权限和目标目录是否正确：

# 源路径末尾的斜杠表示同步目录内容；不写会多出一层目录
sudo rsync -avz --dry-run --delete -e "ssh -p 10022" \
  /data/gitlab/git-data/repositories/ \
  root@192.0.2.10:/data/gitlab/git-data/repositories/

确认无误后执行正式同步（--info=progress2 输出整体进度，-P 支持断点续传）：

sudo rsync -avzP --delete --info=progress2 -e "ssh -p 10022" \
  /data/gitlab/git-data/repositories/ \
  root@192.0.2.10:/data/gitlab/git-data/repositories/

大仓库首次同步可能持续数十分钟到数小时，建议在 tmux 或 nohup 中执行，避免终端断开导致传输中断。

4.3 权限与属主

rsync -a 会保留属主，但**只有 root 才有权将文件 chown 为 git:git**。因此：

  • 使用 root@ 同步：属主自动保留，不需要再执行 chown；
  • 使用普通账号（如 admin_gitlab@）同步：文件属主会变为该账号，必须在新服务器修正；
  • 使用普通账号且不希望事后修正：增加 --rsync-path="sudo rsync"，由远端以 sudo 接收。

使用普通账号时的前置准备：

# 新服务器：将迁移账号加入 git 组
sudo usermod -aG git admin_gitlab
sudo chmod 2770 /data/gitlab/git-data
# 重新登录使组权限生效
id admin_gitlab    # 输出中应包含 git 组

同步完成后统一修正属主与权限（2770 中的 setgid 位保证新建文件继承 git 组）：

sudo chown -R git:git /data/gitlab/git-data/repositories
sudo chmod 2770 /data/gitlab/git-data

sudo ls -lh /data/gitlab/git-data/     # 应为 drwxrws--- git git

属主不是 git:git 时，Gitaly 会报权限错误，网页端仓库返回 500。这是迁移过程中最常见的故障。

4.4 可选：预演轻量备份与恢复

不停机时，可先用 SKIP=repositories 执行一次备份并尝试恢复，以验证流程是否可行。

# 旧服务器：只备份数据库和元数据
sudo gitlab-rake gitlab:backup:create SKIP=repositories,prometheus

需要注意，该备份包的数据不一致：备份过程中可能产生新的提交、MR 和用户，恢复后可能与仓库文件不匹配。它仅用于验证命令与备份格式，不能作为最终数据。

如果已做过预演，且担心新服务器残留数据影响正式迁移，可在正式迁移前重置实例（会清空该实例所有数据）：

sudo gitlab-ctl stop
sudo gitlab-ctl cleanse      # 恢复到刚安装完成的状态
sudo gitlab-ctl reconfigure
sudo gitlab-ctl start

恢复时 restore 会覆盖数据库中的同名数据，但不会删除”备份中不存在、实例中已存在”的对象。为保证结果可预期，建议在干净实例上执行一次恢复，避免在预演数据上叠加。

五、正式迁移（停机窗口）

该阶段需要提前通知并约定窗口时间。整体时间线如下：

阶段 操作 参考耗时
T+0 通知停止提交，停旧服务器 sidekiq、puma 1 分钟
T+1 增量 rsync（只差最后几个提交） 5~15 分钟
T+2 轻量备份（SKIP=repositories，几百 MB） 2~5 分钟
T+3 传输备份包到新服务器 1~5 分钟
T+4 停新服务器写入服务 → restore → 启动 5~15 分钟
T+5 IP 验证 → 切换 DNS → 域名验证 → 通知恢复使用 10~30 分钟（含 DNS 生效）

5.1 旧服务器停机

先停 sidekiq（后台任务，会写入数据库），再停 puma（Web 服务）。顺序不强制，但必须在确认无人使用后执行：

# 停止后网页与代码推送均不可用，执行前需已完成通知
sudo gitlab-ctl stop sidekiq
sudo gitlab-ctl stop puma

5.2 同步增量

sudo rsync -avzP --delete --info=progress2 -e "ssh -p 10022" \
  /data/gitlab/git-data/repositories/ \
  root@192.0.2.10:/data/gitlab/git-data/repositories/

--delete 会删除新服务器上多余的文件，使两边内容一致。此步骤之后不要启动旧服务器，否则会产生新的写入，与仓库文件不一致。

5.3 备份除仓库外的数据

sudo gitlab-rake gitlab:backup:create SKIP=repositories,prometheus

产物位于 gitlab.rb 中 backup_path 指定的目录，文件名形如：

1730000000_2026_10_21_17.5.1_gitlab_backup.tar

备份目录属主为 git:root、权限为 700，因此 scp 需使用 sudo 读取。

5.4 传输备份包并放置到位

# 先传到用户家目录，避免直接写入 git 私有目录
sudo scp -P 10022 /data/gitlab/backups/1730000000_2026_10_21_17.5.1_gitlab_backup.tar \
  admin_gitlab@192.0.2.10:~/

# 新服务器：移入正式备份目录并修正权限
sudo mv ~/1730000000_2026_10_21_17.5.1_gitlab_backup.tar /data/gitlab/backups/
sudo chown git:git /data/gitlab/backups/1730000000_2026_10_21_17.5.1_gitlab_backup.tar
sudo chmod 600      /data/gitlab/backups/1730000000_2026_10_21_17.5.1_gitlab_backup.tar

sudo ls -lh /data/gitlab/backups/     # -rw------- git git

备份包权限不正确时，restore 会报 Permission denied 或找不到备份，该步骤不可省略。

如果文件超过堡垒机/中转机限制（常见为 20 GB），可分片传输后再合并，并校验一致性：

# 旧服务器分片
split -b 5000M -d -a 3 1730000000_2026_10_21_17.5.1_gitlab_backup.tar backup_part_
sha256sum 1730000000_2026_10_21_17.5.1_gitlab_backup.tar > backup.sha256

# 新服务器合并后校验
cat backup_part_* > 1730000000_2026_10_21_17.5.1_gitlab_backup.tar
sha256sum -c backup.sha256     # 输出必须为 OK

5.5 新服务器恢复

再次确认仓库属主（使用 root 同步时可跳过）：

七、常见问题

7.1 rsync 报 some files/attrs were not transferred (code 23)

该报错与网络无关，原因是扫描与传输之间文件被修改或删除（GitLab 在后台写入仓库，即典型的 file vanished）。处理方式：

  • 正式迁移时 GitLab 已停止，无新的写入，该报错不会出现；
  • 预同步阶段改用 root 执行，或使用非 root 账号 + --rsync-path="sudo rsync"，避免因权限不足读取文件而报 23。

7.2 rsync 之后是否需要修正属主

取决于传输账号：

传输方式 是否需要 chown -R git:git
root@ + -a 不需要，属主自动保留
admin_gitlab@ + -a 需要，否则属主变为 admin_gitlab，Gitaly 读写失败
admin_gitlab@ + --rsync-path="sudo rsync" 不需要

chmod 2770 建议每次执行，操作成本低，可避免权限问题。

7.3 备份包的权限是否需要修正

需要。gitlab-backup 生成的备份包权限为 -rw------- git git，手工 scp/mv 后可能丢失权限或改变属主：

sudo chown git:git <包名>.tar
sudo chmod 600      <包名>.tar

7.4 restore 报错找不到备份

BACKUP= 后只写文件名前缀，不带 _gitlab_backup.tar：

# 正确写法
sudo gitlab-rake gitlab:backup:restore BACKUP=1730000000_2026_10_21_17.5.1
# 错误写法
sudo gitlab-rake gitlab:backup:restore BACKUP=1730000000_2026_10_21_17.5.1_gitlab_backup.tar

7.5 页面返回 502 或域名无法访问

按以下三层排查：

  1. 本地 DNS 缓存（Windows 常见）：执行 ipconfig /flushdns；
  2. 新服务器 nginx/puma 是否处于 run 状态：sudo gitlab-ctl status；
  3. external_url 是否与访问域名一致：sudo grep external_url /etc/gitlab/gitlab.rb。

7.6 不停机备份数据库是否可行

可以，但只能用于演练。不停机时数据库与仓库文件处于不同时间点，恢复后会出现”仓库中没有对应提交记录””MR 指向不存在的分支”等不一致。正式迁移必须停止 sidekiq 与 puma。

7.7 如何确认数据未遗漏

使用 4.1 的脚本在迁移前后各执行一次，对比最后一列时间：

sudo gitlab-rails runner /tmp/list_last_commit.rb | sort > /tmp/last_commit.after.txt
diff /tmp/last_commit.before.txt /tmp/last_commit.after.txt

diff 无输出表示所有项目的最后提交时间一致；有输出时需逐条确认差异属于”预期内的新提交”还是”数据遗漏”。

其他校验信号：

  • 备份包大小、sha256 前后一致；
  • 新服务器 du -sh repositories 与旧服务器接近（差异不应达到 GB 级）；
  • 网页端项目数、用户数、Runner 数量一致。

7.8 迁移后旧服务器是否可以启动

在验证通过且域名切换成功之前不要启动。启动后会产生新的写入，两边数据分叉，回滚将变得复杂。

九、小结

本次迁移中耗时的主要不是命令执行，而是三件事：

  1. 版本一致性：流程必须是”同版本恢复 → 再升级”，不能直接安装新版本；
  2. 仓库与元数据分离：将几十 GB 的仓库从备份中排除，改用 rsync 传输，停机窗口从数小时缩短到半小时左右；
  3. 权限与密钥：git:git + 2770 与 gitlab-secrets.json 任一处理不当，表现都是服务正常启动但仓库返回 500、用户无法登录，且报错信息不直观。

升级方面，遵循”逐级升级、每步验证、跨大版本先改配置”三条规则，并为 PostgreSQL 升级预留足够时间与磁盘空间。

小程序踩坑

一、webview打开页面

  1. webview打开的页面需要在小程序中配置为业务域名，即需要在对应的服务器根目录下放置校验文件，需要https（应该），所以如果内部跳转其他页面，而没有配置域名，则会提醒该页面无法打开，即使是微信官方自己的页面
  2. webview跳转客服，因为跳转客服要么使用按钮，并设置open-type，要么使用对应的api跳转，但都没办法在webview中使用，所以可以先跳转到小程序页面（跳转的api在webview中可以调用，官方文档有，但是需要先判断是否在小程序环境内），再跳转到客服（企业微信客服的话，一般是一个work.weixin.qq.com的域名，携带客服id跳转，需要用api调用，且事先在小程序中配置对应的企业微信，需要企业id）
  3. webview打开视频，在小程序（部分浏览器）中打开视频，一般不能设置自动播放，官方避免用户无感知时浪费太多流量，需要用户点击操作后才能播放视频，可以在用户点击按钮后，再使用video.play()触发视频播放
  4. webview打开pdf文件，ios环境下可以直接打开，安卓环境下，则会空白，需要在小程序页面中，执行wx.download和wx.opendocument(应该是这个)，先下载文件，再打开；其中下载时需要先设置下载后的本地路径，才能通过后一个api打开，临时路径无法打开；又因为这是下载文件，所以需要把文件对应的域名加到下载域名下（是否需要校验不确定），所以这里的pdf域名需要配置业务域名（ios用），和下载域名（安卓用）；个人操作，是在h5页面中，判断，若是pdf路径，则跳转到新的webview页面，然后再webview页面中判断，若是pdf路径且安卓，则执行下载并打开，若是ios，则直接显示
