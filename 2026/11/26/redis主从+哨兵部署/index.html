redis主从+哨兵部署

Redis 主从 + Sentinel 哨兵部署实践

内网离线环境下，用源码编译部署一主一从 Redis，并在三台服务器上运行 Sentinel 实现自动故障转移。
文中 IP、主机名、密码、账号均为示例（192.0.2.x / node-a / 【Redis密码】），请替换为实际环境。

写在前面

适用场景：内网自建 Redis，服务器无法访问外网，操作系统为国产化发行版（Kylin V10 / aarch64 同类环境），需要主从复制加自动故障转移，但不使用 Redis Cluster 分片。

版本：Redis 8.10.0（源码编译，仅核心版）；Sentinel 与 Redis 同一套二进制。

节点规划：两台数据库服务器承担一主一从，一台应用服务器只运行 Sentinel，共三个哨兵满足 quorum=2 的要求。

核心结论：

  1. Sentinel 只负责监控与故障转移，不存储数据、不分片；数据仍由主从复制同步，容量上限等于单机内存。
  2. 哨兵数量建议为 3 个，quorum 设为 2：既能在单点故障时完成选举，又能避免出现两个哨兵互相认定对方失联的脑裂。
  3. 离线 + 国产化系统只编译核心版（MALLOC=libc，不加载 modules），完整编译常因模块依赖失败。
  4. 应用必须通过 Sentinel 获取主节点地址，不能写死主节点 IP，否则故障转移后仍连旧主。

以下按”架构规划 → 安装 Redis → 配置主从 → 自启与日志 → 部署 Sentinel → 故障转移验证 → 运维 → 常见问题 → 检查清单”展开。

一、架构与规划

1.1 节点与角色

节点 角色 监听端口 说明
node-a 192.0.2.10 Redis 主节点 + Sentinel 6379 / 26379 写入入口
node-b 192.0.2.11 Redis 从节点 + Sentinel 6379 / 26379 只读，主挂后可能被提升
node-c 192.0.2.12 仅 Sentinel 26379 应用服务器，装 Redis 只为获得 redis-sentinel 二进制

数据流与发现关系：

应用 → Sentinel（三节点 :26379）→ 查询 mymaster → 当前主节点 A:6379
                                     ↑
                        A(6379) ──复制──▶ B(6379)

1.2 端口与防火墙

  • 6379：只对从节点和应用服务器开放，不要对全网段开放；
  • 26379：三台哨兵之间必须互通，否则 sentinels=3 永远不成立。
sudo iptables -L -n --line-numbers

# 以主节点 node-a 为例：允许从节点与本机哨兵访问 6379
sudo iptables -I INPUT 5 -p tcp -s 192.0.2.11 --dport 6379 -j ACCEPT
sudo iptables -I INPUT 6 -p tcp -s 192.0.2.12 --dport 6379 -j ACCEPT

sudo service iptables save
sudo iptables -L -n --line-numbers

云环境还需要在安全组中同步放行，iptables 与安全组是两道独立的限制。

1.3 部署顺序

  1. 两台数据库服务器安装并编译 Redis；
  2. 配置主从并验证复制；
  3. 配置 systemd 自启与日志轮转；
  4. 三台服务器部署 Sentinel（第三台同样需要 Redis 二进制）；
  5. 验证哨兵互相发现；
  6. 做一次主动故障转移演练。

二、安装 Redis

2.1 下载地址与编译依赖

源码包：

内容 地址
Redis 8.10.0 源码 https://download.redis.io/releases/redis-8.10.0.tar.gz
全部版本索引 https://download.redis.io/releases/
下载入口页 https://redis.io/downloads/

索引目录中同时提供 8.10.x 的补丁版本（8.10.1 / 8.10.2 / 8.10.3）与更高次要版本（如 8.12.x）。本文示例沿用部署时的 8.10.0，新建环境建议直接使用所在 minor 系列的最新补丁版本，升级时保持 minor 不变、只做补丁级变更。

编译依赖：

依赖 用途 是否必需
gcc 编译 必需
make 构建 必需
glibc-devel 编译所需的头文件与链接库 必需
tar、gzip 解压源码包 必需
openssl-devel 启用 TLS 相关功能时使用 可选
tcl 仅 make test 需要 可选

检查是否已安装：

gcc --version
make --version
rpm -q glibc-devel

离线环境获取依赖：从系统安装 ISO 的 Packages 目录或内部 yum 源安装，例如麒麟 V10 的软件源目录：

https://update.cs2c.com.cn/NS/V10/V10SP3/os/adv/lic/base/aarch64/Packages/
sudo yum install -y gcc make glibc-devel
# 完全离线时先用 yumdownloader 或从 ISO 拷贝依赖包，再本地安装
sudo yum localinstall -y ./gcc-*.rpm ./make-*.rpm ./glibc-devel-*.rpm

校验：Redis 官方 releases 目录只提供源码包本身，没有独立的 .sha256 旁文件。下载后记录文件大小（ls -l）并与索引页显示值比对；经过堡垒机中转时，建议在内部制品库再计算一次 sha256sum 并留档。

sha256sum redis-8.10.0.tar.gz

2.2 编译与安装

sudo mkdir -p /usr/local/redis
sudo chown -R $(whoami):$(whoami) /usr/local/redis
sudo chmod 755 /usr/local/redis

通过堡垒机把源码包上传到 /usr/local/redis，然后解压：

cd /usr/local/redis
sudo tar xzf redis-8.10.0.tar.gz
cd redis-8.10.0

离线环境与国产化系统上，完整编译常常卡在模块依赖（如 jemalloc、RedisJSON 等）。只编译核心并强制使用 libc 分配器：

cd src
sudo make MALLOC=libc -j$(nproc)
sudo make PREFIX=/usr/local/redis install

安装后的目录结构：

/usr/local/redis/bin/redis-server
/usr/local/redis/bin/redis-cli
/usr/local/redis/bin/redis-sentinel   → 通常是 redis-server 的链接

验证：

/usr/local/redis/bin/redis-server --version
/usr/local/redis/bin/redis-cli --version
ls -l /usr/local/redis/bin/

2.3 数据与日志目录

数据与日志放在数据盘，避免系统盘被 RDB/AOF 写满：

sudo mkdir -p /data/redis/data /data/redis/logs
sudo chown -R $(whoami):$(whoami) /data/redis
sudo chmod -R 755 /data/redis
touch /data/redis/logs/redis-server.log

三、配置主从

3.1 关键配置项

修改 /usr/local/redis/redis-8.10.0/redis.conf：

配置项 建议值 说明
bind 0.0.0.0 监听所有网卡；如网络规划允许，改为具体内网地址更安全
protected-mode no 关闭保护模式，访问控制由 requirepass 与防火墙承担
port 6379
daemonize yes 与 Type=forking 的 systemd 单元配合
pidfile /data/redis/redis_6379.pid 指向数据盘，避免权限问题
logfile /data/redis/logs/redis-server.log
dir /data/redis/data RDB/AOF 落盘位置
requirepass 强密码 主从都需设置
masterauth 与主节点密码一致 从节点必须配置，否则复制报 NOAUTH

3.2 主节点配置

requirepass 【Redis密码】
bind 0.0.0.0
protected-mode no
port 6379
daemonize yes
pidfile /data/redis/redis_6379.pid
logfile /data/redis/logs/redis-server.log
dir /data/redis/data

注释掉 loadmodule 相关配置，因为当前只安装了核心版，没有模块文件。

3.3 从节点配置

除主节点的基础配置外，额外增加：

# 初始拓扑指向主节点；哨兵接管后会被自动改写
replicaof 192.0.2.10 6379

# 主节点设置了 requirepass 时必须配置
masterauth 【Redis密码】

replicaof 只是初始拓扑。哨兵完成一次故障转移后会重写该配置，届时手工修改可能被覆盖，正确做法是通过哨兵变更拓扑。

3.4 关于脑裂防护

min-replicas-to-write 要求”至少 N 个从节点在线才允许写入”。本架构只有一主一从，主节点一旦与从节点失联，在线从节点数为 0，该配置会导致主节点拒绝所有写入，反而扩大故障范围，因此保持默认关闭：

# min-replicas-to-write 0
# min-replicas-max-lag 10

若后续扩展为”一主多从”，再考虑开启。

3.5 启动与验证

两台服务器分别启动：

/usr/local/redis/bin/redis-server /usr/local/redis/redis-8.10.0/redis.conf
ps -ef | grep redis-server | grep -v grep

查看复制状态：

REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli -p 6379 INFO replication

主节点预期输出：

role:master
connected_slaves:1
slave0:ip=192.0.2.11,port=6379,state=online,offset=...,lag=0

从节点预期输出：

role:slave
master_host:192.0.2.10
master_link_status:up

master_link_status:down 时依次检查：主节点密码是否与 masterauth 一致、6379 是否放行、replicaof 地址是否正确。

3.6 数据同步测试

主节点写入：

REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli -p 6379 SET test_key "hello_redis"

从节点读取：

REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli -h 192.0.2.11 -p 6379 GET test_key

返回 hello_redis 即主从复制正常。从节点默认 replica-read-only yes，写入会报 READONLY。

四、systemd 自启与日志轮转

4.1 停止脚本

Redis 由 systemd 托管且配置了 Restart=always，直接 kill 会被自动拉起。停止脚本从配置文件读取密码，避免把密码明文写进 unit 文件：

sudo tee /usr/local/redis/bin/redis-stop.sh > /dev/null <<'SCRIPT'
#!/bin/bash
CONF=/usr/local/redis/redis-8.10.0/redis.conf
PASS=$(awk '/^[[:space:]]*requirepass[[:space:]]/ {print $2; exit}' "$CONF" \
  | sed -e 's/^"//' -e 's/"$//' -e "s/^'//" -e "s/'$//")
if [ -z "$PASS" ]; then
  echo "redis-stop: requirepass not found or empty in $CONF" >&2
  exit 1
fi
REDISCLI_AUTH="$PASS" /usr/local/redis/bin/redis-cli shutdown
SCRIPT

sudo chmod 700 /usr/local/redis/bin/redis-stop.sh
sudo chown root:root /usr/local/redis/bin/redis-stop.sh

4.2 服务单元

# /etc/systemd/system/redis.service
[Unit]
Description=Redis Server
After=network.target

[Service]
Type=forking
ExecStart=/usr/local/redis/bin/redis-server /usr/local/redis/redis-8.10.0/redis.conf
ExecStop=/usr/local/redis/bin/redis-stop.sh
Restart=always

[Install]
WantedBy=multi-user.target

启用：

sudo systemctl daemon-reload
sudo systemctl enable redis
sudo systemctl start redis
sudo systemctl status redis

该单元未指定 User=，服务以 root 运行。如需改为专用账号，需同时调整 /data/redis 属主、pidfile 与日志文件属主，并确认该账号对 /data/redis 有读写权限。

4.3 日志轮转

sudo tee /etc/logrotate.d/redis > /dev/null <<'EOF'
/data/redis/logs/redis-server.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
EOF

使用 copytruncate 的原因是无需向 Redis 发送重开日志的信号，也就不需要在轮转脚本中处理密码；代价是轮转瞬间可能丢失少量日志。

强制轮转并触发一条日志确认新文件生效：

sudo logrotate --force /etc/logrotate.d/redis
REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli CONFIG SET loglevel verbose
REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli CONFIG SET loglevel notice
ls -l /data/redis/logs/

五、部署 Sentinel

5.1 为什么第三台也要装 Redis

Sentinel 由 redis-sentinel 启动，该文件来自 Redis 安装包。第三台应用服务器不需要运行 Redis 实例，但需要这份二进制，因此同样执行第二节的编译安装，只是不启动 redis-server。

5.2 配置目录与文件

三台服务器都执行：

sudo mkdir -p /usr/local/redis/sentinel /data/redis/sentinel
sudo chown -R $(whoami):$(whoami) /usr/local/redis/sentinel /data/redis/sentinel
sudo chmod 700 /usr/local/redis/sentinel

sudo touch /usr/local/redis/sentinel/sentinel.conf
sudo chmod 600 /usr/local/redis/sentinel/sentinel.conf
sudo chown $(whoami):$(whoami) /usr/local/redis/sentinel/sentinel.conf

5.3 sentinel.conf

# /usr/local/redis/sentinel/sentinel.conf
port 26379
daemonize yes
pidfile /data/redis/sentinel/sentinel.pid
logfile /data/redis/sentinel/sentinel.log
dir /data/redis/sentinel

# mymaster 为集群名称，三台必须完全一致
sentinel monitor mymaster 192.0.2.10 6379 2

# 与 Redis 的 requirepass 保持一致
sentinel auth-pass mymaster 【Redis密码】

# 5 秒无响应判定主观下线
sentinel down-after-milliseconds mymaster 5000
# 故障转移超时时间
sentinel failover-timeout mymaster 60000
# 每次只允许一个从节点与新主同步
sentinel parallel-syncs mymaster 1

参数含义：

参数 作用
monitor ... 2 2 是 quorum：至少 2 个哨兵认可主节点失联，才进入客观下线
auth-pass 哨兵连接 Redis 时使用的密码，必须与 requirepass 一致
down-after-milliseconds 主观下线判定时间，过小会误判、过大会延长故障窗口
failover-timeout 同一次故障转移的最长处理时间，也用于抑制重复切换
parallel-syncs 新主产生后同时向新主同步的从节点数量，设为 1 可降低新主压力

Sentinel 运行中会重写该文件，追加 myid、known-sentinel、known-replica 等内容。需要调整参数时优先使用 SENTINEL SET，避免在哨兵运行时直接编辑配置文件。

5.4 启动与集群验证

三台都启动：

/usr/local/redis/bin/redis-sentinel /usr/local/redis/sentinel/sentinel.conf

查看任一哨兵的视图：

/usr/local/redis/bin/redis-cli -p 26379 INFO sentinel

预期：

sentinel_masters:1
master0:name=mymaster,status=ok,address=192.0.2.10:6379,slaves=1,sentinels=3
  • sentinels=3：三个哨兵已互相发现；
  • slaves=1：哨兵已识别到从节点；
  • status=ok：主节点可达。

查看其他哨兵的信息：

/usr/local/redis/bin/redis-cli -p 26379 SENTINEL sentinels mymaster

sentinels=1 说明只有自己，通常是 26379 端口未互通，或三台配置里的 mymaster 名称不一致。

5.5 服务单元与日志轮转

# /etc/systemd/system/redis-sentinel.service
[Unit]
Description=Redis Sentinel
After=network.target

[Service]
Type=forking
PIDFile=/data/redis/sentinel/sentinel.pid
ExecStart=/usr/local/redis/bin/redis-sentinel /usr/local/redis/sentinel/sentinel.conf
ExecStop=/usr/local/redis/bin/redis-cli -p 26379 shutdown
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

先停掉手工启动的实例，再交给 systemd：

/usr/local/redis/bin/redis-cli -p 26379 shutdown
sudo systemctl daemon-reload
sudo systemctl enable --now redis-sentinel
sudo systemctl status redis-sentinel

日志轮转：

sudo tee /etc/logrotate.d/redis-sentinel > /dev/null <<'EOF'
/data/redis/sentinel/sentinel.log {
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    copytruncate
}
EOF

sudo logrotate --force /etc/logrotate.d/redis-sentinel

六、故障转移验证

6.1 记录当前主节点

/usr/local/redis/bin/redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

输出两行：IP 与端口，记下当前主节点。

6.2 停止主节点

sudo systemctl stop redis

systemctl stop 会阻止 Restart=always 自动拉起，因此这是模拟宕机的正确方式；直接 kill 进程会被 systemd 重启。

6.3 观察切换

# 哨兵日志中应出现 +sdown（主观下线）→ +odown（客观下线）→ +switch-master
sudo tail -f /data/redis/sentinel/sentinel.log

# 查询新的主节点
/usr/local/redis/bin/redis-cli -p 26379 SENTINEL get-master-addr-by-name mymaster

+switch-master 行会打印旧主与新主地址，从节点的角色同时发生改变。

6.4 验证新主可写、旧主可回

在新主上写入：

REDISCLI_AUTH='【Redis密码】' /usr/local/redis/bin/redis-cli -h 192.0.2.11 -p 6379 SET test-write-check 1

启动原主节点：

sudo systemctl start redis

哨兵会把它重新配置为从节点，原主节点上执行 INFO replication 应显示 role:slave 且 master_host 指向新主。若原主仍为 master，检查哨兵日志与 failover-timeout，必要时等待一次完整切换周期。

6.5 应用侧接入方式

应用不应写死主节点地址，而应通过哨兵获取：

# Spring Boot 示例
spring:
  data:
    redis:
      password: 【Redis密码】
      sentinel:
        master: mymaster
        nodes: 192.0.2.10:26379,192.0.2.11:26379,192.0.2.12:26379
// Jedis 示例（不同版本 API 略有差异）
JedisSentinelPool pool = new JedisSentinelPool(
    "mymaster",
    Set.of("192.0.2.10:26379", "192.0.2.11:26379", "192.0.2.12:26379"),
    new JedisPoolConfig(),
    "【Redis密码】");

七、运维要点

7.1 停止与修改配置

由于配置了自动重启，停止服务需用 systemctl stop，并确认进程与端口都已释放：

sudo systemctl stop redis
ps -ef | grep redis-server | grep -v grep
ss -tlnp | grep 6379

# 修改配置后
sudo systemctl start redis

7.2 避免手工修改被托管的配置

  • redis.conf 中的 replicaof 会被哨兵改写；
  • sentinel.conf 运行中会被追加 myid、已知哨兵、已知从节点等信息。

调整哨兵参数使用：

/usr/local/redis/bin/redis-cli -p 26379 SENTINEL SET mymaster down-after-milliseconds 5000

7.3 密码与权限

  • redis.conf 建议 600，sentinel.conf 同样 600；
  • 密码通过 REDISCLI_AUTH 环境变量传递，避免出现在 ps 与 shell history 中；
  • 对外只开放必要的来源网段，不应将密码作为唯一防线。

7.4 容量与持久化

  • 容量上限为单机内存，maxmemory 与淘汰策略需按业务设置；
  • 数据盘要预留 RDB 快照与 AOF 重写的空间，日志同样放在数据盘；
  • 内存不足时先扩容而不是依赖哨兵，哨兵只解决可用性问题。

八、常见问题

8.1 编译失败（jemalloc 或模块相关）

离线环境与国产化系统上，完整编译依赖较多。只编译核心：

cd src
sudo make distclean
sudo make MALLOC=libc -j$(nproc)
sudo make PREFIX=/usr/local/redis install

8.2 从节点报 NOAUTH 或复制不建立

  • 从节点 masterauth 是否与主节点 requirepass 一致；
  • 主节点 bind 与 protected-mode 是否允许从节点连接；
  • 主节点 6379 是否对从节点放行。

8.3 客户端提示连接被拒绝

protected-mode yes 且未设置 bind 允许地址时，Redis 只接受本机连接。确认 bind 与 protected-mode 的组合，并检查 iptables 与安全组。

8.4 哨兵只看到自己（sentinels=1）

  • 26379 是否三台互通；
  • 三台配置中 mymaster 名称是否完全一致；
  • 是否存在重复启动的哨兵进程占用不同配置文件。

8.5 主节点宕机但没有触发切换

  • quorum 是否满足：三个哨兵中至少两个判定客观下线；
  • down-after-milliseconds 是否过大；
  • 哨兵日志中是否出现 +sdown 但缺少 +odown（说明另一台哨兵未认可）。

8.6 日志没有轮转

  • 检查 /etc/logrotate.d/redis、redis-sentinel 是否存在且语法正确；
  • 使用 copytruncate 时不需要 create，若同时存在可能产生空文件；
  • 手动执行一次 logrotate --force 观察输出。

8.7 故障转移后应用仍连旧主

应用写死了主节点地址。改为只配置哨兵地址与 mymaster 名称，由客户端库完成主节点发现。

十、小结

本次部署的要点集中在三处：

  1. 编译取舍：离线与国产化环境下只编核心版，避免在模块依赖上耗时；
  2. **哨兵是”发现层”而非”存储层”**：三个哨兵解决的是故障转移与客户端发现，容量与性能仍需靠主从与硬件；
  3. 配置一致性：requirepass/masterauth、mymaster 名称、26379 互通、copytruncate 日志轮转，任一处不一致都会表现为”复制正常但切换不生效”或”日志写满磁盘”。
