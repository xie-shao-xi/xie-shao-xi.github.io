svn迁移

SVN 仓库迁移实战：dump/load、分批传输与权限切换

内网 Subversion 实例的整体迁移记录：仓库 dump/load、大仓库按版本区间分段、账号与权限文件迁移、svnWebUI 管理端重建。
文中域名、IP、账号、仓库名、路径均为示例（svn.example.com / 192.0.2.x / admin_svn / project-a），请替换为实际环境。

写在前面

适用场景：内网自建 Subversion，采用 svnserve 模式（非 Apache mod_dav_svn），配套 svnWebUI 管理端与 Nginx 反向代理；服务器无法访问外网，需离线安装；仓库位于独立数据盘。

环境：ARM64（aarch64）+ 类 RHEL8（el8）发行版；Subversion 1.12.2；新旧服务器版本一致，中间通过堡垒机中转，单文件下载上限 20 GB。

核心结论：

  1. 仓库使用 svnadmin dump / svnadmin load 迁移，不直接拷贝目录，便于压缩传输、按版本分段与逐段校验。
  2. 大仓库按版本区间分段导出，否则单个 dump 文件可能超过中转限制。
  3. 仓库之外的四类数据必须一并迁移：conf/hooks、全局 authz/passwd、svnWebUI 的 sqlite.db，以及证书与配置文件；遗漏任何一类都会导致用户无法登录或权限失效。

以下按”现状盘点 → 方案选型 → 备份 → 新服务器准备 → 加载 → 验证 → 切换域名 → 常见问题 → 检查清单”展开。

一、迁移前确认

1.1 盘点仓库现状

先确认仓库数量、体积与最新版本号，用于估算备份时长和传输方式。

cd /data/svn/data/project/repo

# 各仓库体积（authz、passwd 是文件，不是仓库）
du -sh */

# 各仓库最新版本号与最后一次提交信息
for r in project-a project-b project-c project-d project-e project-f; do
  echo "=== $r ==="
  rev=$(svnlook youngest "$r")
  echo "最新版本: r$rev"
  svnlook info -r "$rev" "$r"
  echo
done

svnlook info 输出作者、提交时间与提交说明，可据此判断各仓库最近是否仍在使用。若多数仓库的最后提交时间距今较远，可按 1.3 的方式先做不停机的全量预演。

1.2 需要迁移的四类内容

内容 旧服务器位置 迁移方式
仓库数据 repo/<仓库名> svnadmin dump → svnadmin load
仓库配置与钩子 repo/<仓库名>/conf、repo/<仓库名>/hooks tar 打包 → 解压覆盖
全局账号与权限 repo/authz、repo/passwd tar 打包 → 解压 → 修正权限位
Web 管理端数据 project/sqlite.db、log、temp tar 打包 → 解压 → 修正属主

注意 authz/passwd 位于仓库根目录（/data/svn/data/project/repo/），不在单个仓库内；各仓库 conf/svnserve.conf 通过相对路径引用它们，因此解压后需要确认相对路径仍然有效。

1.3 是否需要停机

两种做法：

  • 仓库最近无提交：可以不停机完成全量 dump/load 预演，切换域名前再补一次增量（见 8.7），最后统一停止旧服务。
  • 仓库仍在活跃使用：建议在约定窗口内停止 svnserve 与 svnWebUI 后再 dump，避免 dump 过程中产生新版本导致与 conf 时间点不一致。

无论哪种方式，域名切换完成前旧服务不要重新对外开放写入。

二、方案选型

方案 A：一次性全量 dump 方案 B：按版本区间分段 dump 方案 C：服务器间直接 rsync
适用 单仓库体积小于中转上限 大仓库，单个 dump 超过 20 GB 新旧服务器网络互通，不经堡垒机
传输 中转机上传下载 分段后分别传输、分别 load rsync 直接推送
复杂度 低 中，需保证 load 顺序 低，但要求网络可达
本次采用 小仓库 大仓库 备选

分段的核心是 --deltas --incremental：第一段使用 --deltas，后续段追加 --incremental，load 时严格按顺序执行，否则版本号会错乱。

三、备份（旧服务器）

3.1 准备备份目录

sudo mkdir -p /data/svn-dump
sudo chown admin_svn:admin_svn /data/svn-dump

3.2 记录版本基线

备份前记录各仓库最新版本号，加载完成后用于比对。

cd /data/svn/data/project/repo
for r in project-a project-b project-c project-d project-e project-f; do
  echo "$r: r$(svnlook youngest "$r")"
done | tee /tmp/svn-youngest-before.txt

3.3 打包配置与钩子

cd /data/svn/data/project/repo

# 各仓库的 conf 与 hooks
for r in project-a project-b project-c project-d project-e project-f; do
  tar czf /data/svn-dump/${r}-conf.tar.gz -C "$r" conf hooks
done

# 全局账号与权限文件（含敏感信息，注意保管）
tar czf /data/svn-dump/svn-global-conf.tar.gz authz passwd

ls -lh /data/svn-dump/*-conf.tar.gz /data/svn-dump/svn-global-conf.tar.gz

3.4 小仓库直接 dump

cd /data/svn/data/project/repo

for r in project-a project-b project-c; do
  echo ">>> $(date '+%F %T') dumping $r ..."
  svnadmin dump "$r" --deltas | gzip -1 > /data/svn-dump/${r}.dump.gz
  echo ">>> $(date '+%F %T') $r 完成"
  ls -lh /data/svn-dump/${r}.dump.gz
done

--deltas 让 dump 以增量表示存储，体积明显小于默认的全量表示；gzip -1 以较低压缩率换取更高的压缩速度，适合大仓库。

3.5 大仓库后台 dump

单个仓库 dump 可能持续数小时，放入后台执行并记录日志：

nohup bash -c '
  cd /data/svn/data/project/repo
  for r in project-d project-e; do
    echo ">>> $(date) dumping $r"
    svnadmin dump "$r" --deltas | gzip -1 > /data/svn-dump/${r}.dump.gz
    echo ">>> $(date) $r done"
  done
' > /data/svn-dump/dump.log 2>&1 &

tail -f /data/svn-dump/dump.log

3.6 按版本区间分段 dump

当单个仓库的 dump 文件超过中转限制时，按版本区间切分。以下示例将仓库拆为 0、1-5、6-10、11、12 五段：

nohup bash -c '
REPO=/data/svn/data/project/repo/project-d
DUMP_DIR=/data/svn-dump
LOG=$DUMP_DIR/dump_project_d.log

echo ">>> $(date) start 0:0" >> "$LOG"
(svnadmin dump "$REPO" -r 0 --deltas | gzip -1 > "$DUMP_DIR/project-d.0.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 1:5" >> "$LOG"
(svnadmin dump "$REPO" -r 1:5 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.1-5.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 6:10" >> "$LOG"
(svnadmin dump "$REPO" -r 6:10 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.6-10.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 11" >> "$LOG"
(svnadmin dump "$REPO" -r 11 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.11.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) start 12" >> "$LOG"
(svnadmin dump "$REPO" -r 12 --deltas --incremental | gzip -1 > "$DUMP_DIR/project-d.12.dump.gz") >> "$LOG" 2>&1

echo ">>> $(date) all done" >> "$LOG"
' &

tail -f /data/svn-dump/dump_project_d.log

分段原则：

  • 段与段之间必须首尾相接，不重不漏（0、1-5、6-10…）；
  • 只需第一段不带 --incremental，其余段都带；
  • 某一段体积仍超限时，继续按更小的版本区间细分，不要改用 split 切分 dump 文件：分片无法单独校验，出问题时难以定位。

3.7 校验与传输

在旧服务器生成校验值，下载到本地、上传到新服务器后分别校验，三处结果必须一致。校验文件使用相对路径记录，便于在新服务器同目录下复核：

cd /data/svn-dump
md5sum *.dump.gz > md5.txt

# 新服务器：将 md5.txt 与 dump 文件放在同一目录后执行
cd /home/admin_svn/svn-import
md5sum -c md5.txt

若单个文件仍需经堡垒机中转：

split -b 5000M -d -a 3 project-d.0.dump.gz project-d.0.part_
cat project-d.0.part_* > project-d.0.dump.gz

Windows 侧可用 certutil -hashfile <文件> MD5 计算校验值。

四、新服务器准备

4.1 数据盘配置为 LVM 并挂载到 /data

sudo pvcreate /dev/vdb
sudo vgcreate vg_data /dev/vdb
sudo lvcreate -l 100%FREE -n lv_data vg_data

sudo mkfs.xfs /dev/vg_data/lv_data

sudo mkdir -p /data
sudo mount /dev/vg_data/lv_data /data

fstab 中使用 UUID（设备名可能变化）：

sudo blkid /dev/vg_data/lv_data
sudo cp /etc/fstab /etc/fstab.bak
sudo vim /etc/fstab
# 末尾追加（UUID 替换为上一条命令输出的值）
# UUID=【你的UUID】 /data xfs defaults 0 0
sudo mount -a
df -h /data

4.2 离线安装 Subversion

服务器无法访问外网，需提前下载 rpm 及其依赖（以 Kylin V10 / aarch64 为例）：

apr-1.7.0-4.ky10.aarch64.rpm
apr-util-1.6.1-14.ky10.aarch64.rpm
httpd-2.4.43-13.p03.ky10.aarch64.rpm
httpd-filesystem-2.4.43-13.p03.ky10.noarch.rpm
httpd-help-2.4.43-13.p03.ky10.noarch.rpm
httpd-tools-2.4.43-13.p03.ky10.aarch64.rpm
libserf-1.3.9-14.ky10.aarch64.rpm
mod_http2-1.15.13-1.ky10.aarch64.rpm
subversion-1.12.2-4.ky10.aarch64.rpm
utf8proc-2.5.0-1.ky10.aarch64.rpm
web-assets-filesystem-5-1.ky10.noarch.rpm
web-assets-httpd-5-1.ky10.noarch.rpm
sudo yum localinstall *.rpm --disablerepo=* -y

# 验证，应输出 1.12.2
svnserve --version
svnadmin --version

httpd 仅为满足 subversion 的 rpm 依赖，本方案使用 svnserve 模式，不需要 Apache。若安装时被自动启用，关闭即可：

sudo systemctl stop httpd
sudo systemctl disable httpd

4.3 创建运行账号与目录

sudo groupadd admin_svn
sudo useradd -g admin_svn -m -d /home/admin_svn -s /bin/bash admin_svn

# 目录结构与旧服务器保持一致
sudo mkdir -p /data/svn/data/project/repo
sudo chown -R admin_svn:admin_svn /data/svn

路径必须与旧服务器一致：各仓库 conf/svnserve.conf 中以相对路径引用全局 authz/passwd，svnWebUI 的启动参数 --project.home 也依赖该结构。

4.4 放行端口

svn:// 使用 3690，管理端与仓库浏览通过 Nginx 的 443。

sudo iptables -L -n --line-numbers

sudo iptables -I INPUT 19 -p tcp -s 0.0.0.0/0 --dport 443  -j ACCEPT
sudo iptables -I INPUT 20 -p tcp -s 0.0.0.0/0 --dport 3690 -j ACCEPT

sudo service iptables save
sudo iptables -L -n --line-numbers

安全建议：3690 仅对内网网段开放；如不需要直连 svn://，可只放行 443 并通过 Nginx 代理。

firewalld 环境：

sudo firewall-cmd --add-port=443/tcp  --permanent
sudo firewall-cmd --add-port=3690/tcp --permanent
sudo firewall-cmd --reload

4.5 编译安装 Nginx

svnWebUI 的页面通过 Nginx 提供 HTTPS 与反向代理。先确认编译依赖：

gcc --version
make --version
rpm -q pcre-devel zlib-devel openssl-devel
tar -xzf nginx-1.30.6.tar.gz
cd nginx-1.30.6
./configure --prefix=/usr/local/nginx \
  --with-http_ssl_module \
  --with-http_stub_status_module \
  --with-http_realip_module
make -j$(nproc)
sudo make install

证书放置：

sudo mkdir -p /usr/local/nginx/conf/cert
sudo tar xzf ~/cert-current.tar.gz -C /usr/local/nginx/conf/cert/
sudo chmod 600 /usr/local/nginx/conf/cert/server.key

nginx.conf 中与 SVN 管理端相关的配置（省略与本次迁移无关的 location）：

server {
    listen       443 ssl;
    # 域名与 IP 同时写入，便于切换前用 IP 验证
    server_name  svn.example.com 192.0.2.10;

    ssl_certificate      /usr/local/nginx/conf/cert/server.pem;
    ssl_certificate_key  /usr/local/nginx/conf/cert/server.key;
    ssl_protocols        TLSv1.2;
    ssl_ciphers          HIGH:!aNULL:!MD5:!kRSA;
    ssl_prefer_server_ciphers on;

    location / {
        proxy_pass         http://127.0.0.1:8080;
        proxy_redirect     http:// https://;
        proxy_set_header   Host            $host:$server_port;
        proxy_set_header   X-Real-IP       $remote_addr;
        proxy_set_header   X-Forwarded-For $proxy_add_x_forwarded_for;
        client_max_body_size 2048m;
        proxy_connect_timeout 60s;
        proxy_read_timeout    600s;
        proxy_send_timeout    600s;
        if (-d $request_filename) {
            rewrite ^/(.*)([^/])$ /$1$2/ permanent;
        }
    }
}
sudo /usr/local/nginx/sbin/nginx -t
sudo /usr/local/nginx/sbin/nginx

4.6 安装 JDK（svnWebUI 依赖）

sudo mkdir -p /usr/local/java
sudo chown -R $(whoami):$(whoami) /usr/local/java
# 通过堡垒机上传 JDK 压缩包后
sudo tar -zxvf OpenJDK11U-jdk_aarch64_linux_hotspot_11.0.32.1_1.tar.gz -C /usr/local/java/
sudo chmod 755 /usr/local/java

在 /etc/profile 末尾追加：

export JAVA_HOME=/usr/local/java/jdk-11.0.32.1+1
export PATH=$JAVA_HOME/bin:$PATH
source /etc/profile
java -version

五、加载数据（新服务器）

5.1 单个仓库的完整流程

cd /data/svn/data/project/repo

svnadmin create project-a
gzip -dc /home/admin_svn/svn-import/project-a.dump.gz | svnadmin load project-a
svnadmin verify project-a

# 恢复该仓库的 conf 与 hooks
tar xzf /home/admin_svn/svn-import/project-a-conf.tar.gz -C /data/svn/data/project/repo/project-a

# 确认相对路径未被改变
grep -E 'authz-db|password-db' /data/svn/data/project/repo/project-a/conf/svnserve.conf
# 应指向 ../../authz 与 ../../passwd，且未被注释

svnadmin verify 会重放全部版本，仓库越大耗时越长，但这是确认 dump 完整性的直接方式，不建议跳过。

5.2 分段仓库按顺序 load

cd /data/svn/data/project/repo
svnadmin create project-d

nohup bash -c '
  cd /data/svn/data/project/repo
  for f in project-d.0 project-d.1-5 project-d.6-10 project-d.11 project-d.12; do
    echo ">>> $(date) loading $f ..."
    gzip -dc /home/admin_svn/svn-import/${f}.dump.gz | svnadmin load /data/svn/data/project/repo/project-d
    echo ">>> $(date) $f done"
  done
  echo ">>> $(date) all load done, starting verify ..."
  svnadmin verify /data/svn/data/project/repo/project-d
  echo ">>> $(date) verify done"
' > /home/admin_svn/svn-import/load-project-d.log 2>&1 &

tail -f /home/admin_svn/svn-import/load-project-d.log

顺序必须与 dump 时的版本区间顺序一致（0 → 1-5 → 6-10 → 11 → 12）。顺序错误或漏段时，load 会因版本号冲突失败或产生错误的历史。

加载完成后可直接查看最新版本号：

svnlook youngest /data/svn/data/project/repo/project-d

同时恢复该仓库的配置：

tar xzf /home/admin_svn/svn-import/project-d-conf.tar.gz -C /data/svn/data/project/repo/project-d
grep -E 'authz-db|password-db' /data/svn/data/project/repo/project-d/conf/svnserve.conf

5.3 恢复全局账号与权限

只需执行一次，覆盖到仓库根目录：

tar xzf /home/admin_svn/svn-import/svn-global-conf.tar.gz -C /data/svn/data/project/repo

chmod 600 /data/svn/data/project/repo/passwd
chmod 644 /data/svn/data/project/repo/authz
ls -l /data/svn/data/project/repo/authz /data/svn/data/project/repo/passwd

权限位需与旧服务器保持一致：passwd 含明文或哈希密码，仅属主可读；authz 需被 svnserve 进程可读。

5.4 版本比对

全部加载完成后，与 3.2 记录的基线比对：

for r in project-a project-b project-c project-d project-e project-f; do
  echo "$r: r$(svnlook youngest "/data/svn/data/project/repo/$r")"
done | tee ~/svn-youngest-after-load.txt

diff ~/svn-youngest-before.txt ~/svn-youngest-after-load.txt

diff 无输出表示各仓库版本号一致。

5.5 恢复 svnWebUI 数据

必须先恢复 sqlite.db 再首次启动 svnWebUI：管理端启动时可能按默认逻辑重写账号文件，顺序错误会导致 authz/passwd 被覆盖。

sudo tar xzf /home/admin_svn/svn-import/svnwebui-data.tar.gz -C /data/svn/data/project

cd /data/svn/data/project
chown admin_svn:admin_svn sqlite.db
chmod 640 sqlite.db
ls -l sqlite.db

六、运行与验证

6.1 启动 svnserve

svnserve -d -r /data/svn/data/project/repo --listen-port 3690

ss -tlnp | grep 3690

6.2 验证仓库访问

用测试账号逐个仓库验证读取权限：

for r in project-a project-b project-c project-d project-e project-f; do
  echo "=== $r ==="
  svn ls "svn://localhost/$r" --username <测试账号>
done

验证日志与历史：

svn log -l 5 svn://localhost/project-a --username <测试账号>

6.3 启动 svnWebUI

nohup java -Xms512m -Xmx2g -Dfile.encoding=UTF-8 \
  -jar /data/svn/svnWebUI-1.8.9.jar \
  --server.port=8080 \
  --project.home=/data/svn/data/project \
  > /data/svn/nohup.log 2>&1 &

tail -f /data/svn/nohup.log

启动后确认账号文件未被覆盖：

wc -c /data/svn/data/project/repo/passwd /data/svn/data/project/repo/authz

与迁移前的字节数对比，若明显变小，说明被管理端重建，需要用备份文件恢复后重新检查管理端配置。

6.4 验证 HTTPS 与管理端

curl -k -I https://localhost

浏览器访问 https://192.0.2.10/adminPage/login，使用迁移前的管理员账号登录，确认用户列表、仓库列表与权限规则完整。

6.5 停止顺序

维护或回滚时按以下顺序停止：

pkill -f svnWebUI-1.8.9.jar
pkill svnserve
/usr/local/nginx/sbin/nginx -s quit

先停管理端与 svnserve，最后停 Nginx，避免代理层继续转发到已停止的服务。

七、切换域名与收尾

  1. 提前与运维确认 DNS 切换方式与工单流程；
  2. 切换前用 IP 完成第六节的全部验证；
  3. 切换后将 svnWebUI 中记录的仓库地址、钩子脚本中的地址一并核对，避免仍指向旧 IP；
  4. 通过域名验证管理端登录与 svn checkout；
  5. 旧服务器保持停机但保留数据，作为回滚手段；
  6. 观察一段时间后再清理旧服务器。

回滚方式：DNS 切回旧服务器并启动旧服务。需要注意，切换后在新服务器上产生的新版本无法通过回滚带回旧服务器，因此回滚窗口应尽量短。

八、常见问题

8.1 能否直接拷贝仓库目录

可以在同版本、同路径的前提下用 svnadmin hotcopy 或直接复制目录，但要求两端路径完全一致、版本一致，且无法在传输中压缩和分段。使用 dump/load 可以获得可校验的中间产物，并在加载时逐段确认，更适合跨机器、跨中转的迁移。

8.2 单个 dump 文件超过中转限制

三种处理方式，按优先级：

  1. 按版本区间分段 dump（3.6），最易校验；
  2. split 分片传输后合并，合并后必须校验 md5/sha256；
  3. 新旧服务器网络互通时改用 rsync 直接传输，绕过堡垒机。

8.3 分段 load 顺序错误会怎样

load 会因版本号不连续报错，或把后续段加载到错误的版本上。判断方法：加载完成后用 svnlook youngest 与基线比对，并抽查 svn log 的版本号连续性。

8.4 恢复 conf/hooks 后相对路径失效

svnserve.conf 中的 authz-db、password-db 是相对 conf/ 目录的路径。只要新服务器目录结构与旧服务器一致（repo/<仓库>/conf 与 repo/authz、repo/passwd 的相对关系不变），路径即有效。恢复后统一用以下命令确认：

grep -E 'authz-db|password-db' /data/svn/data/project/repo/*/conf/svnserve.conf

8.5 迁移后用户无法登录

依次确认：

  1. 全局 passwd 是否恢复到位，权限是否为 600；
  2. 各仓库 svnserve.conf 的 password-db、authz-db 是否指向正确的全局文件；
  3. svnserve 进程是否有权限读取上述文件（admin_svn 属主）；
  4. 若账号由 svnWebUI 维护，确认 sqlite.db 已恢复且启动顺序正确（5.5）。

8.6 svnWebUI 启动后账号或权限文件被改写

管理端启动时可能依据数据库重建 authz/passwd。规避方式：

  • 先恢复 sqlite.db 再启动管理端；
  • 启动后立即用 wc -c 对比文件大小；
  • 保留一份 authz.bak.$(date +%F)、passwd.bak.$(date +%F) 作为回退。

8.7 迁移期间有人提交

对仍在使用的仓库，在切换窗口内先停止服务，再以迁移前记录的基线版本为起点导出增量并加载（示例中基线为 r100）：

svnadmin dump /data/svn/data/project/repo/project-a \
  -r 101:HEAD --deltas --incremental | gzip -1 > /data/svn-dump/project-a.inc.dump.gz

加载顺序仍为”全量段 → 增量段”。

8.8 如何确认数据完整

四项交叉验证：

  • svnlook youngest 与基线一致；
  • svnadmin verify 无报错；
  • md5sum -c 校验通过（旧服务器、本地、新服务器三处一致）；
  • svn log 抽查最新版本与提交人、提交说明。

十、小结

本次迁移的主要工作量集中在三处：

  1. 备份与分段：仓库总量与中转上限决定了必须按版本区间拆分，分段之间的版本衔接和 load 顺序是正确性的关键；
  2. 仓库之外的配套数据：conf/hooks、全局 authz/passwd、sqlite.db 的体积都很小，但缺失或顺序错误会直接表现为”用户无法登录、权限失效”，排查成本高于迁移本身；
  3. 验证方式：svnlook youngest 比对、svnadmin verify、md5 三处校验、svn log 抽查，四项结合才能确认内容与历史都完整。

迁移流程本身并不复杂，主要风险来自”只迁了仓库，忘了配套文件”和”分段顺序错误”两类问题。
